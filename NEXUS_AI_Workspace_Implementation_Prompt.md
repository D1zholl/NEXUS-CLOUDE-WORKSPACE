# ЧАСТЬ I. ОСНОВНОЙ ПРОМТ ДЛЯ AI-РАЗРАБОТЧИКА

## 1. Роль и конечная задача

Ты — ведущий архитектор и senior full-stack разработчик, которому поручено внедрить **NEXUS AI Workspace** в существующий проект **NEXUS Workspace**.

Разработай и внедри новый полноценный модуль платформы, объединяющий два режима работы:

1. **AI Chat** — обычный диалог пользователя с выбранной моделью PolyStrata, без доступа модели к инструментам Agent Mode.
2. **AI Agent** — выполнение многошаговых задач агентом: анализ запроса, выбор доступных Skills и инструментов, запрос подтверждений для рискованных действий, исполнение на отдельном компьютере через NEXUS AI Runtime, получение результатов и продолжение цикла до завершения задачи.

NEXUS AI Workspace состоит из двух самостоятельных программных компонентов:

- **NEXUS AI Backend** — модуль `ai` внутри существующего backend NEXUS на основном сервере. Он отвечает за данные, права, диалоги, историю, планирование и оркестрацию задач, подтверждения, квоты, аудит, администрирование, связь с Runtime и публикацию событий.
- **NEXUS AI Runtime** — отдельное Windows-приложение/служба на втором компьютере, где запущен PolyStrata. Runtime устанавливает исходящее защищённое соединение с NEXUS, получает задания, вызывает локальный PolyStrata, исполняет строго разрешённые инструменты в выделенных рабочих каталогах и возвращает результаты.

**Критерий результата:** пользователь должен иметь возможность открыть NEXUS AI Workspace, вести потоковый диалог с PolyStrata, переключиться в Agent Mode, поручить агенту реальную задачу с файлами или зарегистрированными программами на втором компьютере, наблюдать каждый шаг, подтвердить опасные операции, отменить задачу и получить сохранённый результат. Администратор должен контролировать Runtime, модели, пользователей, рабочие пространства, Skills, инструменты, программы, квоты и журнал действий.

Не делай демонстрационную реализацию. Не добавляй декоративные кнопки, фиктивные статусы, моковые ответы вместо реальных механизмов или функции, которые выглядят рабочими, но ничего не выполняют.

## 2. Неприкосновенные правила разработки

1. **Не переписывай существующие подсистемы.** Сначала выясни, как устроены текущие auth, RBAC, storage, jobs, realtime, system settings, audit, monitoring и API. Расширяй их по действующим соглашениям.
2. Сохраняй существующую работоспособность Minecraft Build Manager, NEXUS Cloud Storage и System Management. Любое изменение общих механизмов должно быть минимальным, обоснованным и покрытым регрессионными тестами.
3. Не создавай параллельную реализацию авторизации, ролей, WebSocket-брокера, аудита, мониторинга, файлового движка или фонового планировщика, если подходящий механизм уже существует. Исключение — отдельная безопасность и протокол Runtime, если они не могут безопасно использовать пользовательскую сессию.
4. Все права проверяются на backend и повторно в Runtime на границе исполнения. Скрытие кнопки на frontend не является контролем доступа.
5. Ни один запрос модели, текст Skill, файл, результат MCP, содержимое сайта, stdout/stderr программы или другой внешний ввод не может расширить права агента или изменить системную политику.
6. Не используй пользовательскую браузерную cookie-сессию для Runtime. Устройство должно иметь отдельную регистрацию и отдельный отзывной токен.
7. Не открывай входящие порты на компьютере Runtime. Runtime сам устанавливает исходящее соединение с NEXUS по защищённому WebSocket (`wss://` в production).
8. Не предоставляй агенту права локального администратора и не запускай произвольный CMD/PowerShell по свободному тексту модели.
9. Все состояния диалогов, задач, подтверждений и исполнений, необходимые для восстановления, должны надёжно сохраняться в PostgreSQL. Нельзя полагаться только на RAM процесса или Runtime.
10. При невозможности закончить требование полностью явно отметь его как незавершённое. Не подменяй реализацию заглушкой и не объявляй этап завершённым только потому, что проект компилируется.

## 4. Архитектура платформы и интеграция с NEXUS

### 4.1. Существующая платформа — базовые ограничения

Ориентируйся на действующую архитектуру NEXUS Workspace:

- единый self-hosted модульный монолит backend;
- Rust stable, edition 2024, предпочтительно Rust 1.85+;
- Axum 0.8, Tokio, Tower / tower-http;
- PostgreSQL 14+ и SQLx 0.8 с миграциями;
- React 19, TypeScript, Vite 7, React Router 7;
- TanStack Query и Zustand;
- Lucide React и существующие CSS Variables / структурированные CSS;
- существующий WebSocket `/api/v1/ws`;
- Windows 11 / Windows Server — целевая платформа поставки;
- один активный экземпляр NEXUS на одну БД защищён advisory lock `hashtext('nexus.instance')`.

Платформа уже использует серверные cookie-сессии (`HttpOnly`, `SameSite=Lax`, `Secure` по конфигурации), CSRF через HMAC, Argon2id, RBAC, request ID, централизованные ошибки, журнал событий, системные jobs, мониторинг и объектное хранилище. Переиспользуй эти механизмы после проверки их реальной реализации.

### 4.2. Новый backend-модуль

Добавь изолированный модуль `backend/src/ai/` с логическим разделением как минимум на:

- `mod.rs` — регистрация AI-модуля;
- `routes.rs` — HTTP-маршруты;
- `models.rs` / `dto.rs` — модели и DTO;
- `service.rs` — бизнес-логика;
- `repository.rs` — SQLx-доступ к данным;
- `orchestrator.rs` — жизненный цикл Agent Task и последовательные модельные циклы;
- `provider/` — OpenAI-compatible клиент, адаптер PolyStrata, модели, streaming parser;
- `runtime/` — регистрация узлов, аутентификация, WebSocket протокол, heartbeat, leases, reconnect;
- `tools/` — каталог инструментов, политики, JSON Schema и проверки разрешений;
- `skills/` — импорт, валидация, версии, назначения и доставка Skills;
- `workspaces/` — права, квоты и привязка к Runtime;
- `approvals/` — запросы подтверждений и атомарное потребление подтверждения;
- `events.rs` — интеграция с существующим realtime;
- `errors.rs` — типизированные ошибки AI, совместимые с общей схемой NEXUS.

Это ориентир, а не требование механически создать каждый файл: адаптируй структуру под фактические соглашения кода. Не превращай модуль в один огромный файл.

AI-модуль должен подключаться к общему router/state/middleware и отключаться через системный module gate по аналогии с остальными модулями. При выключенном AI API и исполнение новых задач должны блокироваться сервером без перезапуска. Для уже выполняемых процессов должна быть определена безопасная политика: отменить немедленно либо запретить новые команды и дать администратору управляемо остановить текущие.

### 4.3. Отдельный Runtime

Создай отдельный Rust-проект/пакет, например `runtime/`, со своим `Cargo.toml`, исходниками, конфигурацией, тестами, логированием, сборкой и установкой.

Runtime должен быть самостоятельным Windows executable и Windows Service. Он не должен зависеть от frontend или от процесса NEXUS на своём компьютере.

Рекомендуемые логические части:

- `config` — безопасное чтение конфигурации и секретов;
- `registration` — первоначальная привязка устройства;
- `connection` — WSS, reconnect, heartbeat, идентификация и обмен сообщениями;
- `provider` — HTTP-клиент локального PolyStrata;
- `executor` — диспетчер задач и отмена;
- `tools` — реестр и исполнение инструментов;
- `filesystem` — безопасные операции внутри workspace;
- `process` — запуск зарегистрированных программ и контроль дерева процессов;
- `skills` — получение и загрузка Skills по требованию;
- `mcp` — внешние MCP-подключения, если они разрешены;
- `limits` — CPU/память/время/параллельность/размеры файлов;
- `audit` и `logging` — безопасные журналы без секретов.

Runtime не должен запускать HTTP-сервер для удалённого управления и не должен требовать открытия входящего порта. Единственный управляющий канал — исходящее защищённое соединение с NEXUS.

## 5. Протокол регистрации и связи Backend ↔ Runtime

### 5.1. Первоначальная регистрация

Реализуй административный процесс регистрации устройства:

1. Администратор в System Management создаёт одноразовый registration code для конкретного Runtime/пользователя или группы разрешений.
2. Код имеет ограниченный срок действия, однократное использование и минимально необходимые scopes.
3. Runtime получает код локально через защищённый ввод/конфигурацию и выполняет enrollment-запрос к NEXUS.
4. Backend проверяет код, срок, статус AI-модуля и полномочия администратора, создаёт `runtime_node`.
5. Runtime получает отдельный device token с достаточными, но минимальными правами.
6. В PostgreSQL хранится только безопасный verifier/hash токена; открытый token отображается/выдаётся только в момент создания и не возвращается повторно.
7. Реализуй ротацию токена и немедленный отзыв устройства.

Не используй пользовательскую cookie-сессию браузера, пароль пользователя или общий секрет NEXUS для идентификации Runtime.

### 5.2. WebSocket-соединение

Runtime подключается к выделенной точке, например `/api/v1/ai/runtime/connect`, используя WSS в production и device authentication. Пользовательский WebSocket `/api/v1/ws` остаётся отдельным каналом.

Реализуй:

- проверку токена и статуса устройства на handshake;
- heartbeat с периодом, выбранным через конфигурацию;
- online/offline/degraded/disabled состояние и `last_seen_at`;
- reconnect с exponential backoff и jitter;
- серверное обнаружение разрыва и истечения lease;
- согласование версии протокола и версии Runtime;
- передачу версии Runtime, платформы, версии PolyStrata, списка моделей, инструментов и статуса программ;
- подтверждение получения команд;
- sequence number / event ID для дедупликации и восстановления;
- отмену задачи и подтверждение отмены;
- безопасную передачу ограниченных по размеру payload и потоковых фрагментов;
- закрытие соединения при отзыве токена или отключении Runtime администратором.

### 5.3. Контракт сообщений

Зафиксируй версионированный JSON-контракт. Каждое сообщение должно иметь как минимум:

- `protocol_version`;
- `message_id` — уникальный ID сообщения;
- `type`;
- `timestamp`;
- `node_id`;
- `correlation_id` / `task_id`, когда применимо;
- `sequence` либо иной способ упорядочивания;
- `payload`.

Предусмотри типы сообщений:

- `runtime.hello`, `runtime.hello_ack`;
- `runtime.heartbeat`, `runtime.heartbeat_ack`;
- `runtime.capabilities`, `runtime.capabilities_ack`;
- `task.dispatch`, `task.accepted`, `task.progress`, `task.completed`, `task.failed`, `task.cancel`, `task.cancelled`;
- `provider.chat.start`, `provider.chat.delta`, `provider.chat.completed`, `provider.chat.failed`, `provider.chat.cancel`;
- `tool.execute`, `tool.accepted`, `tool.progress`, `tool.completed`, `tool.failed`;
- `skill.fetch`, `skill.fetch_result`;
- `runtime.error`.

Фактические имена и payload можно уточнить при проектировании, но контракт должен быть документирован в коде и `docs/`. Все операции должны иметь correlation ID, idempotency и проверку владельца/узла. Не доверяй `node_id`, переданному в произвольном payload: он должен соответствовать аутентифицированному устройству.

### 5.4. Восстановление и доставка

- PostgreSQL является источником истины по задачам и состояниям.
- Backend не должен считать отправку WebSocket-сообщения гарантией выполнения.
- Сохраняй задачу до dispatch; Runtime подтверждает принятие.
- Используй lease/claim с временем истечения и ограниченным числом попыток.
- После reconnect Runtime и Backend сверяют состояние активных задач, executions и sequence IDs.
- Повторная доставка одного сообщения не должна приводить к повторному опасному действию.
- Для идемпотентных read-операций допускай безопасный повтор.
- Для write/process/delete операций после неопределённого результата не запускай действие повторно без проверки execution receipt или явного решения пользователя/администратора.
- Если Runtime отключён, новые задачи остаются queued либо получают контролируемую ошибку по политике; пользователь видит понятный статус.

## 6. Интеграция PolyStrata и Provider Layer

### 6.1. Провайдер

Сделай слой `OpenAI-compatible Provider`, не связывай бизнес-логику AI напрямую с конкретным HTTP-форматом PolyStrata.

По умолчанию Runtime обращается к PolyStrata на своей машине:

- Base URL `http://127.0.0.1:8080/v1`;
- `/chat/completions`;
- `/models`;
- `/health`;
- `/status`;
- `/metrics`.

Запросы к модели выполняются с компьютера Runtime, поэтому Backend не должен пытаться обращаться к `127.0.0.1` на основном сервере.

### 6.2. Управление конфигурацией

Администратор может задать:

- имя провайдера и тип `openai-compatible`;
- Base URL;
- API Key (необязательный, если локальный PolyStrata работает без него);
- Runtime Node, через который доступен endpoint;
- выбранную модель по умолчанию;
- `temperature`, `top_p`, `max_tokens` — только если модель поддерживает параметры;
- ограничения контекста и ответа;
- timeout и параметры retry;
- включён/выключен.

API Key хранить только в зашифрованном виде с использованием принятого в проекте механизма управления секретами либо отдельного ключа шифрования из защищённой конфигурации. Не возвращать ключ frontend после сохранения, не писать его в tracing, audit, error details или Runtime-логи.

### 6.3. Функции Provider Layer

Реализуй:

- получение списка моделей;
- проверку соединения и состояния PolyStrata;
- проверку доступности выбранной модели;
- обычный Chat Completions;
- SSE streaming с корректным разбором фрагментов;
- передачу истории сообщений;
- отмену генерации при остановке пользователем;
- обработку сетевых ошибок, timeouts, HTTP errors и некорректного JSON;
- обработку OpenAI function calling;
- поддержку нескольких `tool_calls` за один ответ;
- сохранение `tool_call_id` и корректное добавление результатов инструментов в следующий запрос модели;
- учёт finish reason, usage и ограничений контекста, если PolyStrata возвращает эти поля;
- ограничение числа токенов/символов и размера сообщений;
- контроль частоты, числа параллельных запросов и таймаутов.

Не полагайся только на заявленную OpenAI-совместимость. Валидируй структуру сообщений и tool calls; неправильные или неизвестные вызовы переводить в контролируемую ошибку, а не исполнять.

### 6.4. Разделение Chat и Agent

**AI Chat:** в model request не передавать никакие инструменты Agent Mode, файловые инструменты, программы или MCP. Даже если клиент подменит режим в HTTP-запросе, backend должен сформировать chat request без tools.

**AI Agent:** передавать модели только tools, разрешённые одновременно:

- для текущего пользователя;
- для конкретного workspace;
- для выбранного Runtime;
- глобальной политикой администратора;
- политикой текущего режима и задачи.

Список tools строится сервером, а не принимается от frontend или модели.

## 7. AI Chat — пользовательский функционал

Создай полноценный интерфейс и backend для обычного диалога.

### 7.1. Диалоги и сообщения

Поддержи:

- создание диалога;
- генерацию короткого названия после первого запроса (при ошибке генерации оставить безопасное название по умолчанию);
- хранение владельца, модели, provider, режима и workspace, если он задан;
- список и пагинацию истории;
- поиск по названию и тексту сообщений;
- сортировку по дате активности;
- переименование;
- удаление/архивацию с согласованной политикой восстановления;
- сохранение сообщений user/assistant и вложений;
- повторную генерацию ответа;
- редактирование пользовательского сообщения и повторную отправку с корректным удалением/маркировкой последующих производных сообщений;
- копирование текста и code blocks;
- остановку генерации;
- продолжение истории после перезагрузки браузера и backend restart.

Все диалоги должны быть привязаны к пользователю. Проверяй ownership в каждом repository/service/route сценарии. Нельзя получить чужой диалог или сообщение подменой UUID.

### 7.2. Streaming и сохранность

- Передавай текстовые дельты через существующий realtime механизм или согласованный streaming endpoint.
- Публикуй `ai.message.delta` и `ai.message.completed` адресно владельцу диалога.
- Храни финальное сообщение и при необходимости периодически сохраняй накопленный streaming state, чтобы обрыв соединения не терял весь результат.
- При reconnect frontend запрашивает актуальное сохранённое состояние, а не считает полученные ранее WebSocket-дельты единственной копией.
- Разделяй состояние генерации и текст сообщения: `streaming`, `completed`, `failed`, `cancelled` или согласованный эквивалент.

### 7.3. Форматирование и вложения

- Markdown с безопасным рендерингом;
- подсветка синтаксиса кода;
- корректное отображение длинных строк и блоков;
- копирование сообщений/фрагментов;
- прикрепление файлов с контролем размера и разрешённых типов;
- хранение вложений через существующий Storage Engine или согласованный объектный механизм, не сохраняя произвольный путь пользователя;
- ограничения на количество и общий размер вложений;
- безопасное извлечение текстового содержимого с ограничением объёма и без исполнения HTML/JS/SVG;
- метаданные вложений и связь с сообщением;
- показ выбранной модели и статуса подключения.

## 8. AI Agent — оркестрация задач

### 8.1. Основной цикл агента

Реализуй server-controlled orchestration loop:

1. Принять запрос пользователя в Agent Mode.
2. Проверить `ai.agent.use`, доступ к conversation/workspace, квоты, доступность Runtime и Provider.
3. Создать и сохранить Agent Task в состоянии `queued` до отправки на Runtime.
4. Сформировать system/developer контекст из неизменяемых правил продукта, пользовательского запроса, состояния задачи и разрешённых Skills. Недоверенные данные всегда отделять от системных инструкций.
5. Получить только разрешённые Skills и инструменты текущего пользователя/workspace/runtime.
6. Отправить запрос в PolyStrata через Runtime.
7. Получить текстовый ответ и/или `tool_calls`.
8. Для каждого tool call проверить JSON Schema, доступность инструмента, пользователя, workspace, Runtime, политику риска, квоты, лимиты, idempotency и approval policy.
9. Если нужно подтверждение — сохранить Tool Approval, перевести задачу в `waiting_approval`, уведомить пользователя и остановить дальнейшее исполнение до решения.
10. После разрешения передать конкретный инструмент и проверенные аргументы Runtime.
11. Runtime исполняет инструмент и возвращает структурированный результат, stdout/stderr/метаданные или ошибку с ограничением размера и редактированием секретов.
12. Сохранить Tool Execution и результат.
13. Передать результат обратно модели как tool result.
14. Повторять модельный цикл, пока модель не завершит работу, задача не будет отменена или не будет достигнут лимит.
15. Сохранить финальный ответ, итоговый статус и аудит.

Backend является оркестратором и источником полномочий. Runtime исполняет только конкретную команду, подписанную/аутентифицированную каналом и прошедшую локальную проверку политики. Runtime не должен получать полномочия модели на самостоятельное изменение своего реестра разрешений.

### 8.2. Состояния и переходы

Публичные состояния Agent Task:

- `queued`;
- `running`;
- `waiting_approval`;
- `completed`;
- `failed`;
- `cancelled`.

Определи и реализуй допустимые переходы. Терминальные состояния `completed`, `failed`, `cancelled` не должны самопроизвольно возвращаться в `running`.

Для отображения прогресса храни отдельные поля этапа/подэтапа, текст статуса, счётчик итераций, текущий tool execution и timestamps. Не создавай дополнительные публичные статусы без необходимости.

### 8.3. Ограничения выполнения

Настраиваемые лимиты:

- максимальное число циклов модели/tool calls;
- максимальная длительность задачи;
- timeout одного обращения к модели;
- timeout одного инструмента/процесса;
- максимальное число параллельных задач на пользователя и Runtime;
- максимальный размер tool input/output;
- максимальное число вызовов инструмента в одном цикле;
- пределы контекста и ответа модели;
- retry policy с учётом идемпотентности.

Сохраняй промежуточные результаты и состояние orchestration после каждого существенного шага. Восстановление после рестарта должно продолжать безопасную задачу либо завершать её контролируемой ошибкой, но не дублировать side effects.

### 8.4. Отмена

- Пользователь может отменить собственную задачу при наличии `ai.tasks.cancel`.
- Администратор может аварийно отменить любую задачу в рамках своих полномочий.
- Backend сохраняет cancel request и публикует его Runtime.
- Runtime отменяет HTTP stream/генерацию, завершает соответствующий process tree и возвращает подтверждение.
- Принудительное завершение процесса должно учитывать дочерние процессы и не оставлять фоновые процессы.
- После подтверждённой отмены задача получает `cancelled`; отмена должна быть безопасна и повторяемая.
- Если Runtime недоступен, показывай состояние запроса отмены/ожидания связи и не заявляй об успешной остановке до подтверждения или достоверного завершения процесса.

### 8.5. Восстановление при разрыве

- Используй PostgreSQL для task state, step history, tool execution, approval и lease.
- Runtime reconnect сверяет незавершённые задачи с Backend.
- Неизвестная Backend задача не должна исполняться Runtime.
- Неизвестный Runtime execution не должен автоматически повторяться.
- Если действие могло завершиться до разрыва, но подтверждение не дошло, проверь execution receipt или переведи задачу в контролируемое состояние ошибки/ручной проверки.
- После восстановления интерфейс отображает действительный статус из PostgreSQL.

## 9. Управление инструментами, действиями и подтверждениями

### 9.1. Tool Registry

Создай реестр инструментов на стороне Runtime, а также серверную копию/каталог доступных возможностей для авторизации и отображения в UI.

Каждый инструмент имеет:

- стабильный `tool_id` и версию;
- отображаемое имя и описание;
- JSON Schema входных параметров;
- категорию;
- категорию риска (`low`, `medium`, `high`, `critical` либо эквивалент, согласованный в проекте);
- timeout;
- максимальный размер результата;
- требуемые scopes/permissions;
- policy подтверждения;
- признак доступности;
- признак идемпотентности;
- ограничения на аргументы и файловые области.

Инструмент должен быть deny-by-default. Неизвестный, отключённый или не назначенный инструмент всегда отклоняется.

### 9.2. Файловые инструменты

Реализуй:

- `list_files`;
- `read_file`;
- `write_file`;
- `search_files`;
- `create_directory`;
- `move_file`;
- `copy_file`;
- `delete_file`;
- `apply_patch`.

Требования:

- все пути относительные относительно закреплённого workspace root;
- запрещены абсолютные пути, `..`, UNC paths и выход за root;
- канонизация/нормализация и повторная проверка непосредственно перед действием;
- проверка symlink, junction и Windows reparse points, включая race conditions;
- не следовать ссылкам за пределы workspace;
- лимит размера чтения/записи, числа файлов, глубины поиска и результата;
- атомарная запись через временный файл и безопасную замену там, где это применимо;
- для `apply_patch` проверять целевые файлы, контекст и размер diff; сохранять результат и информацию об изменении;
- массовое удаление/перезапись и другие опасные изменения требуют подтверждения;
- возвращать пользователю относительные пути, не абсолютные пути Runtime.

### 9.3. Запуск программ

Не разрешай модели формировать произвольную shell-команду. Запуск должен проходить только через зарегистрированные программы.

Администратор задаёт для каждой программы:

- `program_id`;
- точный путь к исполняемому файлу;
- разрешённый список аргументов/схему параметров;
- рабочую директорию в пределах workspace;
- разрешённые переменные окружения;
- timeout;
- лимит процессов/ресурсов;
- сетевую политику;
- risk level и необходимость подтверждения.

Поддержи регистрацию, если программа действительно установлена и проверена на Runtime:

- Git;
- Python;
- Node.js;
- npm;
- Rust/Cargo;
- PowerShell;
- FFmpeg;
- Playwright;
- другие программы, добавляемые администратором.

Для каждого запуска сохраняй stdout, stderr, exit code, duration, start/end, process status и ограниченный результат. Реализуй timeout, отмену и завершение всего дерева процессов. Не передавай секреты в аргументах командной строки и не логируй их.

### 9.4. Подтверждения опасных действий

Минимально требуй подтверждение для:

- удаления файлов;
- массовой перезаписи/перемещения/удаления;
- запуска неизвестных или впервые разрешаемых программ;
- выполнения скриптов;
- установки пакетов;
- потенциально опасных системных операций;
- любых действий, риск которых повышен политикой администратора.

Approval должен быть связан с конкретными:

- пользователем;
- task ID;
- tool execution/call ID;
- tool ID и версией;
- точными нормализованными аргументами (хеш параметров);
- сроком действия;
- решением и субъектом, принявшим решение.

Нельзя после одобрения подменить аргументы. Подтверждение одноразовое, атомарно потребляется и истекает. Повторный запрос с другими параметрами требует нового approval.

Настройки auto-approve допускай только для явно доверенных инструментов и заданных администрацией аргументных диапазонов/workspace. Не включай глобальный auto-approve для всех инструментов.

### 9.5. MCP

Для внешних MCP-серверов реализуй реестр соединений, обнаружение инструментов, назначение пользователям/workspace, scopes и индивидуальные политики.

- MCP выключен по умолчанию, пока администратор не зарегистрировал и не разрешил его.
- Каждый обнаруженный tool проходит те же проверки JSON Schema, RBAC, risk и approval, что и локальный инструмент.
- Контролируй адреса сетевых подключений, DNS/IP resolution, loopback/private/link-local диапазоны и SSRF; не допускай неожиданный доступ к внутренним сервисам.
- Не пересылай MCP-серверу системные секреты NEXUS или device token Runtime.
- Результаты MCP являются недоверенными данными.

## 10. Skills

Поддержи навыки в структуре на основе `SKILL.md`, например:

```text
skills/
  frontend-development/
    SKILL.md
    references/
    scripts/
    assets/
```

### 10.1. Управление Skills

Реализуй:

- обнаружение и каталог навыков;
- импорт каталога/архива;
- валидацию структуры;
- просмотр содержимого `SKILL.md` и дополнительных файлов;
- редактирование/обновление с версионированием;
- включение/отключение;
- назначение пользователям и workspace;
- описание зависимостей;
- проверку наличия зависимостей на Runtime;
- доставку Runtime только разрешённого Skill;
- подгрузку Skill по необходимости, а не всего каталога сразу;
- аудит импорта, изменения, назначения и удаления.

Храни метаданные в PostgreSQL; содержимое — через безопасный объектный механизм NEXUS или отдельное контролируемое хранилище после проверки Storage Engine. Не раскрывай пользователю физические серверные пути.

### 10.2. Безопасность Skills

- Содержимое Skills — недоверенные инструкции и данные.
- Skill не может менять system prompt, разрешения, роли, список tools, лимиты или правила подтверждения.
- Скрипты не исполняются автоматически из-за наличия в архиве/каталоге.
- Запуск скрипта разрешается только как зарегистрированный инструмент с отдельной политикой и approval.
- При импорте архива предотвращай zip-slip, path traversal, symlink abuse, чрезмерное распаковывание и недопустимые размеры.
- Проверяй имя, структуру, число файлов и размер всего Skill.
- При передаче модели явно обрамляй текст Skill как недоверенный контекст, не как системную политику.

## 11. Пользовательские рабочие пространства на Runtime

Администратор выделяет каждому пользователю изолированное пространство на конкретном Runtime.

Настройки workspace:

- Runtime Node;
- физический диск/том на стороне Runtime;
- корневой каталог (виден только Runtime и администратору с соответствующими правами; API не раскрывает абсолютный путь обычному пользователю);
- quota дискового пространства;
- лимит числа файлов;
- максимальный размер одного файла;
- лимит параллельных задач;
- максимальное время выполнения;
- список разрешённых Skills;
- список разрешённых tools;
- список доступных программ;
- статус active/suspended;
- владельца и аудит изменений.

### 11.1. Изоляция

- У каждого workspace отдельный root и ACL.
- Пользователь не может выбрать/подменить root через API или аргументы инструмента.
- Проверяй путь после нормализации и непосредственно перед файловой операцией.
- Запрещай traversal, symlink/junction/reparse escape, системные корни и неразрешённые тома.
- Не давай процессу доступ к каталогам других пользователей.
- Запускай процессы от непривилегированной учётной записи/изоляционного контекста.
- Используй Windows Job Objects и доступные системные механизмы контроля дочерних процессов и ресурсов.
- Не запускай агентные процессы от имени администратора.
- Проверяй квоты до и после операции; блокируй операцию, которая превышает квоту.
- Учитывай конкурентные записи/запуски, чтобы гонка не позволяла превысить квоту.
- В ответах API и UI показывай относительные пути, usage и понятные ошибки, но не физический абсолютный путь.

### 11.2. Изоляция от NEXUS Cloud Storage

Не смешивай Runtime workspace с обычным пользовательским Cloud Storage без специального решения после исследования Storage Engine. Для AI workspace должны быть отдельные границы доступа, квот и политики исполнения. Можно переиспользовать Storage Engine как безопасный механизм хранения вложений/артефактов, но не открывать агенту внутренние каталоги объектов NEXUS.

## 12. PostgreSQL и модель данных

Используй текущий PostgreSQL/SQLx стиль, UUID, внешние ключи, индексы, транзакции и новые миграции. Точный набор колонок адаптируй к существующим conventions, но функционально должны быть представлены следующие сущности.

### 12.1. Обязательные таблицы

1. **AI Provider Configurations** (`ai_provider_configs`): provider ID, имя, тип, base URL, encrypted API key, default model, generation settings JSONB, runtime binding, limits, enabled, created/updated by, timestamps.
2. **Runtime Nodes** (`ai_runtime_nodes`): node ID, имя/устройство, token verifier/hash, runtime version, protocol version, platform, status, capabilities JSONB, last heartbeat, registered/revoked timestamps, created by.
3. **Runtime enrollment tokens** (отдельная таблица или эквивалент): одноразовый token hash, expiry, scopes, issuer, used/revoked timestamps.
4. **Conversations** (`ai_conversations`): owner user ID, title, mode (`chat`/`agent`), provider ID, model, workspace ID, runtime node ID, state/metadata, created/updated/deleted timestamps.
5. **Messages** (`ai_messages`): conversation ID, sequence, role, content/structured parts, model, status, usage, attachment refs, tool call metadata, error metadata safe for user, timestamps.
6. **Workspaces** (`ai_workspaces`): owner, runtime node, opaque workspace identifier, quota fields, limits, assignments, status, created/updated by, timestamps. Физический путь не должен выдаваться обычному API.
7. **Agent Tasks** (`ai_tasks`): conversation, owner, runtime node, provider/model, status, current stage, progress, iteration counters, timeout, idempotency key, lease, cancellation state, persisted orchestration data, timestamps.
8. **Tool Executions** (`ai_tool_executions`): task ID, tool call ID, tool ID/version, validated arguments (с редактированием чувствительных полей), risk, approval reference, status, result/artifact refs, error code, duration, idempotency/execution receipt, timestamps.
9. **Tool Approvals** (`ai_tool_approvals`): task/execution, requester, approver, arguments hash, decision, expiry, consumed timestamp, reason, timestamps.
10. **Skills** (`ai_skills`): metadata, version, content object ref, checksum, enabled, dependencies, importer/editor, timestamps.
11. **Skill Assignments** (`ai_skill_assignments`): skill, user/workspace/role scope, enabled, assigned by, timestamps.
12. **User AI Quotas** (`ai_user_quotas`): пользовательские лимиты задач, параллельности, storage/files/max file, execution timeout и дополнительные provider/token limits при наличии достоверного usage.

### 12.2. Дополнительные таблицы по результатам аудита

Добавь, если они нужны для корректной реализации:

- tool definitions / tool policies;
- registered programs и их разрешённые аргументы;
- MCP connections и MCP tool snapshots;
- workspace usage reservations;
- task step/event log;
- idempotency records;
- Runtime command outbox / receipts;
- attachments/artifacts metadata;
- audit links.

Не дублируй существующие таблицы jobs, audit, users, roles, permissions или storage, если можно расширить их безопасно.

### 12.3. Целостность данных

- Внешние ключи и индексы на owner, conversation, task, runtime, status и timestamps.
- Индексы для поиска/пагинации и очереди задач.
- Уникальность sequence в диалоге, idempotency keys и device identifier в рамках принятой модели.
- Транзакции для создания задач, выдачи approval, потребления approval и terminal status.
- Ограничения на длину содержимого/JSON и размеры результатов.
- Мягкое удаление там, где оно требуется для целостности аудита и восстановления.
- Чёткая retention policy для сообщений, логов, artifacts и Runtime receipts.
- Секреты провайдера/device — только зашифрованно или в виде hash/verifier; никогда не plaintext.

## 18. Безопасность — обязательный threat model

Рассматривай Agent Mode как выполнение потенциально опасных операций на пользовательском компьютере. Безопасность должна быть реализована на границах Backend, Runtime, workspace, provider и tool execution.

### 18.1. Базовые меры

- Повторная проверка RBAC на сервере и Runtime.
- Раздельные credentials для пользователя и устройства.
- Короткоживущие одноразовые enrollment codes и отзывные device tokens.
- TLS/WSS для Runtime в production.
- Секреты зашифрованы/хешированы, редактируются в логах и ошибках.
- Валидация входных параметров JSON Schema.
- Ограничения длины, размера, времени, параллельности и частоты.
- Idempotency и дедупликация сообщений/команд.
- Аудит каждого tool execution, approval, изменения policy и доступа.
- Немедленная возможность отключить Runtime и остановить задачи.
- Защита от path traversal, symlink/junction/reparse point escape.
- Изолированные права Windows-пользователя и Job Objects.
- Контроль egress/network для программ и MCP.
- Безопасная обработка архивов, вложений и результатов исполнения.

### 18.2. Prompt injection и недоверенные данные

Считай недоверенными:

- содержимое пользовательских файлов;
- веб-страницы и внешние источники;
- `SKILL.md`, references и assets;
- stdout/stderr;
- результаты MCP;
- имена файлов/каталогов и метаданные;
- tool outputs и сообщения Runtime.

Ни один из этих источников не может:

- менять системные правила;
- выдавать себе новые разрешения;
- изменять allowlist инструментов;
- обходить approval;
- раскрывать секреты, чужие диалоги или чужие workspace;
- заставлять Runtime исполнять произвольную команду.

Разделяй trusted policy и untrusted context в prompt. Перед каждым действием сервер независимо проверяет tool, аргументы, ресурс, scope, риск и approval. Не считай фразу модели «пользователь разрешил» фактическим подтверждением.

### 18.3. Особые угрозы

Покрой тестами:

- подмену conversation/task/workspace/node UUID;
- повторное использование registration code/device token;
- replay WebSocket commands;
- path traversal и symlink/junction race;
- argument injection и shell metacharacters;
- zip-slip и decompression bombs;
- SSRF и MCP access к внутренним адресам;
- превышение workspace quotas при конкурентных операциях;
- двойное выполнение при reconnect/timeout;
- подмену параметров после approval;
- prompt injection из файла/Skill/tool output;
- утечку API Key/token в UI/log/error/audit;
- доступ пользователя к чужим сообщениям, files, tasks и execution logs.

### 21.1. Обязательные функциональные тесты

1. NEXUS подключается к Runtime на другом компьютере.
2. Runtime регистрируется по одноразовому коду; повторное использование кода невозможно.
3. Runtime аутентифицируется отдельным токеном; отзыв токена прекращает доступ.
4. Runtime самостоятельно подключается к NEXUS по WSS без входящего порта.
5. Heartbeat корректно меняет статус online/offline.
6. Runtime обнаруживает доступность PolyStrata через локальный endpoint.
7. Backend получает список моделей через Runtime.
8. AI Chat даёт потоковый ответ и сохраняет историю.
9. Перезагрузка frontend не теряет сохранённый диалог.
10. Повторная генерация и редактирование сообщения работают по заданной политике.
11. Chat Mode не передаёт модели tools.
12. Agent Mode передаёт только разрешённые tools.
13. Агент выполняет несколько последовательных tool calls в одном задании.
14. Агент читает и создаёт файл в разрешённом workspace.
15. Агент выполняет `apply_patch` и возвращает результат.
16. Агент запускает разрешённую зарегистрированную программу и сохраняет stdout/stderr/exit code.
17. Неизвестная программа и неразрешённый tool блокируются.
18. Skill импортируется, валидируется, назначается и используется по необходимости.
19. Skill script не исполняется автоматически.
20. Опасная операция переводится в `waiting_approval`.
21. Approve запускает только точные ранее просмотренные аргументы.
22. Reject/expiry не позволяют исполнить операцию.
23. Отмена генерации и процесса останавливает выполнение.
24. Разрыв WSS и reconnect восстанавливают безопасное состояние.
25. Неопределённый результат side effect не приводит к повторному исполнению.
26. Администратор отключает Runtime и новые/текущие операции блокируются согласно политике.
27. Рабочие пространства пользователей изолированы.
28. Path traversal, absolute path, symlink и junction escape блокируются.
29. Квоты места, файлов, размера, параллельности и времени соблюдаются в гонках.
30. Пользователь не получает чужие диалоги, сообщения, задачи, файлы, approvals и логи.

33. Prompt injection в файле/Skill/tool output не расширяет полномочия.
34. API Key, device token и абсолютные пути не попадают в frontend, audit и журналы.

# ЧАСТЬ II. КОНКРЕТНЫЕ АРХИТЕКТУРНЫЕ ПРАВИЛА, КОТОРЫЕ НЕЛЬЗЯ ПОТЕРЯТЬ

## A. Разделение ответственности

| Компонент | Ответственность | Не должен делать |
|---|---|---|
| NEXUS AI Backend | Пользователи, RBAC, диалоги, история, квоты, Tasks, orchestration, approvals, Skills metadata, tool policies, аудит, события | Не должен обращаться к `127.0.0.1` PolyStrata на удалённом Runtime-хосте; не должен доверять решениям frontend/LLM |
| NEXUS AI Runtime | Устройство, локальный PolyStrata, исполнение tools, доступ к закреплённым workspace, процессы, лимиты, результаты | Не должен самостоятельно выдавать себе права, менять server policy, принимать пользовательскую cookie-сессию или исполнять произвольный shell-текст |
| PolyStrata | Генерация текста и tool-call предложений | Не является источником авторизации и не может самостоятельно исполнять локальные операции |
| PostgreSQL | Источник истины для пользователей, конфигурации, сообщений, задач, approvals, executions и состояний | Не заменяется временным состоянием в памяти Runtime |
| Existing NEXUS realtime | Адресная доставка событий в UI | Не является единственным хранилищем истории или task state |

## B. Путь обычного Chat

1. Frontend отправляет сообщение в AI API.
2. Backend проверяет сессию, CSRF, RBAC, ownership, квоты и выбранный Provider/Runtime.
3. Backend сохраняет user message и generation state.
4. Backend передаёт Runtime команду `provider.chat.start`.
5. Runtime обращается к локальному PolyStrata `/v1/chat/completions`.
6. Runtime передаёт потоковые фрагменты Backend.
7. Backend сохраняет/публикует `ai.message.delta` владельцу диалога.
8. По завершении сохраняет assistant message и публикует `ai.message.completed`.
9. При ошибке/отмене сохраняет фактический результат и статус.

**Инвариант:** Chat request никогда не содержит `tools` Agent Mode.

## C. Путь Agent Task

1. Frontend отправляет agent prompt.
2. Backend создаёт persisted task `queued`.
3. Backend резервирует квоты и Runtime capacity.
4. Backend формирует контекст и разрешённый tools list.
5. Runtime вызывает PolyStrata.
6. Backend получает модельный ответ/tool calls и независимо проверяет каждый вызов.
7. При необходимости сохраняет approval и ставит `waiting_approval`.
8. После approve Backend dispatch-ит проверенную команду Runtime.
9. Runtime ещё раз проверяет локальные ограничения и исполняет tool.
10. Backend сохраняет execution/result, отправляет tool result модели.
11. Цикл продолжается до final answer/лимита/ошибки/cancel.
12. Backend фиксирует terminal state и уведомляет пользователя.

## D. Инварианты исполнения

- Нет allowlist entry — нет выполнения.
- Нет соответствующего permission — нет выполнения.
- Нет workspace assignment — нет доступа к workspace.
- Не совпал arguments hash с approval — нет выполнения.
- Истёк approval — нет выполнения.
- Runtime disabled/revoked — нет новых команд.
- Workspace path не прошёл проверку — нет доступа.
- Достигнут лимит — действие отклоняется до выполнения.
- Нет подтверждения завершения — не утверждать, что side effect завершён.
- Повтор сообщения/команды не должен повторять неидемпотентный side effect.
- LLM tool call — это предложение действия, а не разрешение на него.
