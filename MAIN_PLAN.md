# 1. ЦЕЛЬ ПРОЕКТА

Разработать полноценную веб-платформу NEXUS WORKSPACE для самостоятельного размещения на собственном сервере.

Платформа должна объединять два независимых функциональных пространства:

1. **Minecraft Build Manager** — управление сборками Minecraft, загрузка файлов, формирование манифестов, публикация релизов и предоставление файлов собственному Minecraft-лаунчеру.
2. **NEXUS Cloud Storage** — облачное хранилище пользовательских файлов с возможностью выбора физических дисков сервера, настройки каталогов хранения, загрузки, скачивания, организации файлов и просмотра содержимого.

Дополнительно разработать общую административную систему, отвечающую за пользователей, права доступа, настройки приложения, мониторинг сервера и управление фоновыми процессами.

Основные требования:

- Серверная часть написана на Rust.
- Интерфейс доступен через обычный браузер.
- Все операции выполняются на собственном сервере.
- Не использовать обязательные сторонние облачные хранилища.
- Файлы физически хранятся на указанных дисках сервера.
- Интерфейс соответствует предоставленным изображениям.
- Система должна быть пригодна для постоянной эксплуатации, а не только демонстрации.
- Обеспечить высокую производительность при работе с большими файлами и большим количеством файлов.
- Предусмотреть возможность дальнейшего расширения функционала.

Не создавать упрощённую демонстрацию. Реализовать действующие серверные механизмы, API, базу данных, обработку ошибок, безопасность и пользовательский интерфейс.

# 2. ТЕХНОЛОГИЧЕСКИЙ СТЕК

## 2.1. Backend

Основной язык: **Rust, Edition 2024, Stable Toolchain**.

Использовать следующие технологии:

| Компонент                    | Технология                                                                 |
| ------------------------------------- | ------------------------------------------------------------------------------------ |
| HTTP-сервер                     | Axum                                                                                 |
| Асинхронная среда     | Tokio                                                                                |
| HTTP Middleware                       | Tower + tower-http                                                                   |
| База данных                 | PostgreSQL                                                                           |
| Работа с БД                  | SQLx                                                                                 |
| Сериализация              | Serde / Serde JSON                                                                   |
| Авторизация                | Серверные сессии                                                      |
| Хеширование паролей | Argon2id                                                                             |
| Хеширование файлов   | SHA-256                                                                              |
| WebSocket                             | Axum WebSocket                                                                       |
| Логирование                | tracing                                                                              |
| Конфигурация              | TOML + переменные окружения                                       |
| API-документация          | OpenAPI / Swagger                                                                    |
| TLS                                   | Через обратный прокси и rustls при необходимости |

Использовать асинхронный подход для сетевых запросов и операций ввода-вывода.

Не блокировать основной Tokio Runtime длительными синхронными операциями. Тяжёлые операции хеширования, сканирования файлов и обработки архивов выполнять через ограниченные пулы блокирующих задач.

## 2.2. Frontend

Создать отдельное клиентское приложение:

- React.
- TypeScript.
- Vite.
- Three.js для 3D-фона.
- React Router для маршрутизации.
- TanStack Query для взаимодействия с серверным API.
- Zustand для локального состояния интерфейса.
- Lucide React для иконок.
- CSS Modules или структурированные CSS-файлы с CSS Variables.

Использовать собственную дизайн-систему. Не ограничиваться готовыми шаблонами административных панелей.

## 2.3. Общие требования к стеку

1. Все версии библиотек проверять на совместимость с выбранной стабильной версией Rust и Node.js.
2. Зафиксировать зависимости в Cargo.lock и lock-файле frontend.
3. Не использовать устаревшие библиотеки без технической необходимости.
4. Не использовать Redis и отдельную очередь сообщений на первом этапе без объективной потребности.
5. Обеспечить возможность сборки frontend в статические файлы с последующей раздачей через Rust-сервер или обратный прокси.
6. Основное хранилище метаданных — PostgreSQL. Не использовать JSON-файлы вместо полноценной базы данных для основной информации приложения.

Не создавать тысячи отдельных DOM-элементов или независимых тяжёлых Mesh-объектов без необходимости.

Реализовать:

- Независимую анимацию трансформаций объектов.
- Частичное случайное изменение траекторий.
- Эффект свечения.
- Частицы звёзд.
- Масштабирование сцены под экран.
- Освобождение WebGL-ресурсов при размонтировании.
- Приостановку анимации, когда вкладка неактивна.
- Адаптивное снижение нагрузки при слабой производительности устройства.

# 6. ОБЩАЯ СИСТЕМА ПОЛЬЗОВАТЕЛЕЙ И ПРАВ ДОСТУПА

Создать единый механизм авторизации для двух рабочих пространств.

## 6.1. Авторизация

Реализовать:

- Вход по имени пользователя и паролю.
- Выход.
- Проверку существующей сессии.
- Продление сессии согласно политике безопасности.
- Завершение всех сессий пользователя.
- Смену пароля.
- Блокировку и разблокировку аккаунта.
- Сброс пароля администратором.
- Ограничение числа попыток входа.

Использовать Argon2id для хеширования паролей.

Для браузера использовать безопасные серверные сессии с cookie HttpOnly, Secure и SameSite.

Не хранить JWT, refresh token или пароль в localStorage.

Защитить изменяющие состояние запросы от CSRF.

Регистрация пользователей через публичную форму по умолчанию отключена. Создание аккаунтов выполняет администратор.

Первого администратора создавать через безопасную CLI-команду первоначальной настройки. Не использовать зашитые в коде пароли.

## 6.2. Роли

Стандартные роли:

**Administrator**

- Полный доступ.
- Создание пользователей.
- Настройка прав.
- Управление системой.
- Управление дисками.
- Управление всеми сборками и файлами.
- Просмотр журналов и мониторинга.

**User**

- Доступ только к разрешённым рабочим пространствам.
- Работа со своими файлами.
- Доступ к сборкам в пределах выданных прав.
- Запрет на системные настройки.

Предусмотреть возможность создания дополнительных ролей.

## 6.3. Гибкие разрешения

Не ограничиваться двумя фиксированными ролями.

Создать систему granular permissions.

Примеры:

`minecraft.view`
`minecraft.build.create`
`minecraft.build.edit`
`minecraft.build.publish`
`minecraft.build.delete`
`minecraft.artifacts.upload`

`cloud.view`
`cloud.file.upload`
`cloud.file.download`
`cloud.file.delete`
`cloud.file.share`
`cloud.folder.create`
`cloud.storage.manage`

`system.view`
`system.users.manage`
`system.storage.manage`
`system.settings.manage`
`system.monitoring.view`

Проверка прав должна происходить на сервере для каждого защищённого API-запроса.

Сокрытие кнопок во frontend не считается защитой.

# 7. РАБОЧЕЕ ПРОСТРАНСТВО №1 — MINECRAFT BUILD MANAGER

Создать полноценную административную панель для подготовки сборок Minecraft и передачи необходимых файлов клиентскому лаунчеру.

## 7.1. Назначение

Система должна позволять создавать сборки, наполнять их файлами и формировать манифест, который понимает собственный Minecraft-лаунчер.

Сборка представляет собой набор параметров игры, загрузчика и файлов, которые необходимо установить в каталог конкретной игровой конфигурации.

Сервер не обязан самостоятельно упаковывать всю игру Minecraft.

Манифест должен определять именно те компоненты, которые необходимо загрузить или обновить на клиенте. Базовые игровые библиотеки и assets лаунчер может получать из официальных источников Mojang и загрузчиков.

## 7.2. Главная страница модуля

Отображать:

- Общее количество сборок.
- Количество опубликованных сборок.
- Количество черновиков.
- Количество файлов.
- Общий размер всех артефактов.
- Последние изменения.
- Последние публикации.

Ниже — таблица или карточки сборок.

Каждая сборка содержит:

- Название.
- Идентификатор.
- Иконку.
- Версию Minecraft.
- Тип загрузчика.
- Версию загрузчика.
- Версию релиза.
- Количество файлов.
- Размер.
- Дату изменения.
- Статус.

Предусмотреть:

- Поиск.
- Фильтрацию.
- Сортировку.
- Создание новой сборки.
- Редактирование.
- Клонирование.
- Архивирование.
- Удаление с проверкой ссылок на используемые файлы.

## 7.3. Создание сборки

Создать многоэтапный процесс.

### Шаг 1. Основные данные

Поля:

- Название сборки.
- Уникальный slug.
- Описание.
- Иконка.
- Версия сборки.
- Категория.
- Видимость.
- Статус.

### Шаг 2. Настройка Minecraft

Поле версии Minecraft.

Значения загружать из актуального списка официальных версий.

### Шаг 3. Настройка загрузчика

Поддержать:

- Vanilla.
- Fabric.
- Forge.
- NeoForge.
- Quilt, если он будет поддержан клиентским лаунчером.

Показывать только совместимые версии загрузчиков.

Предусмотреть получение метаданных из официальных источников:

- Mojang.
- Fabric Meta.
- Forge Maven / официальные метаданные Forge.
- NeoForge Maven.

Запросы выполнять через backend с кешированием и обработкой ошибок внешнего API.

Не использовать HTML-парсинг сторонних сайтов вместо официальных API или метаданных.

### Шаг 4. Требования к Java

Указать:

- Требуемую основную версию Java.
- Минимальную версию Java.
- Дополнительные требования, если они есть.

Валидация должна учитывать совместимость выбранной игровой версии и загрузчика.

### Шаг 5. Наполнение сборки файлами

Это одна из главных функций модуля.

Поддержать следующие категории:

1. Mods — моды.
2. Config — конфигурации.
3. Resourcepacks — текстурпаки.
4. Shaderpacks — шейдеры.
5. Scripts — дополнительные скрипты и данные.
6. Overrides — произвольные файлы и каталоги.
7. Other — дополнительные материалы.

Интерфейс должен иметь файловый менеджер сборки.

Возможности:

- Загрузка отдельных файлов.
- Множественная загрузка.
- Drag & Drop.
- Загрузка целых папок с сохранением относительной структуры.
- Создание папок.
- Перемещение файлов внутри структуры сборки.
- Переименование.
- Удаление.
- Замена содержимого.
- Просмотр информации.
- Поиск.
- Фильтрация по категории.
- Отображение размера.

Основные типы файлов:

- `.jar`
- `.zip`
- `.json`
- `.toml`
- `.cfg`
- `.properties`
- `.txt`
- `.png`
- `.json5` и другие форматы, если они нужны конкретным модам.

Не запускать загружаемые `.jar`, скрипты или другие файлы на сервере.

Различать оригинальное имя файла и внутренний идентификатор бинарного объекта.

### Шаг 6. Настройки отдельных файлов

Для каждого файла хранить:

- Имя.
- Относительный путь.
- Категорию.
- Размер.
- SHA-256.
- Идентификатор объекта хранения.
- Целевую сторону: client / server / both.
- Обязательность установки.
- Включён / отключён.
- Дополнительное описание.
- Дату загрузки.

Проверять, что пути внутри сборки:

- Не содержат `..`.
- Не содержат абсолютных путей.
- Не позволяют выйти за пределы каталога игровой конфигурации.
- Не конфликтуют с другими файлами.
- Сохраняют совместимость с целевой платформой.

Проверять дубли путей с учётом регистра и нормализации Unicode.

### Шаг 7. Проверка сборки

Перед публикацией выполнить автоматическую проверку:

- Заполнены основные поля.
- Выбрана версия Minecraft.
- Выбран допустимый загрузчик.
- Версии загрузчика и игры совместимы.
- Все обязательные файлы существуют.
- Размеры файлов корректны.
- SHA-256 рассчитаны.
- Нет конфликтующих путей.
- Нет повреждённых объектов.
- Все ссылки на хранилище доступны.
- Указаны требования к Java.
- Нет недействительных записей в манифесте.

Вывести список ошибок и предупреждений.

Ошибки блокируют публикацию. Предупреждения могут быть приняты администратором с подтверждением.

## 7.4. Версионирование и релизы

Реализовать систему релизов.

Одна сборка может иметь несколько релизов.

Например:

- 1.0.0
- 1.0.1
- 1.1.0
- 2.0.0

Статусы:

- Draft.
- Validating.
- Ready.
- Published.
- Archived.
- Deprecated.

Опубликованный релиз должен быть неизменяемым.

При изменении опубликованной сборки необходимо создавать новый релиз.

Старые релизы должны оставаться доступными, пока администратор явно не удалит их и пока на них существуют необходимые ссылки.

Предусмотреть:

- Историю изменений.
- Changelog.
- Список изменённых файлов.
- Сравнение релизов.
- Откат текущего релиза на предыдущую версию.
- Отключение распространения устаревшего релиза.

## 7.5. Формирование манифеста

Создать собственный документированный формат манифеста с обязательным полем `schema_version`.

Пример:

```json
{
  "schema_version": "1.0",
  "build": {
    "id": "build-uuid",
    "slug": "create-expert",
    "name": "Create Expert",
    "release": "1.0.0",
    "changelog": "Initial release"
  },
  "minecraft": {
    "version": "1.20.1"
  },
  "loader": {
    "type": "forge",
    "version": "47.4.10"
  },
  "java": {
    "major": 17
  },
  "files": [
    {
      "id": "artifact-uuid",
      "path": "mods/example.jar",
      "category": "mod",
      "side": "client",
      "required": true,
      "size": 1024000,
      "sha256": "file-sha256",
      "download_url": "/api/v1/launcher/artifacts/artifact-uuid"
    },
    {
      "id": "artifact-uuid-2",
      "path": "config/example.toml",
      "category": "config",
      "side": "client",
      "required": true,
      "size": 4096,
      "sha256": "file-sha256",
      "download_url": "/api/v1/launcher/artifacts/artifact-uuid-2"
    }
  ]
}
```

Это пример контракта. Финальную JSON-схему необходимо оформить отдельно и документировать.

Требования:

- Манифест генерируется автоматически из БД.
- Сервер не отправляет клиенту абсолютные пути к файлам.
- Все пути являются относительными путями игровой сборки.
- Для каждого файла указывается SHA-256.
- Для каждого файла указывается фактический размер.
- Ссылки на скачивание доступны через серверный API.
- Поддерживается версия схемы манифеста.
- Повторная генерация одного и того же опубликованного релиза должна давать одинаковое логическое содержимое манифеста.
- Предусмотреть будущую возможность добавления delta-обновлений.

Не записывать в манифест локальные пути дисков сервера.

## 7.6. API для собственного лаунчера

Создать отдельную группу API, предназначенную для подключения Minecraft-лаунчера.

Пример:

```text
GET /api/v1/launcher/catalog

GET /api/v1/launcher/builds

GET /api/v1/launcher/builds/{slug}

GET /api/v1/launcher/builds/{slug}/releases

GET /api/v1/launcher/builds/{slug}/latest/manifest

GET /api/v1/launcher/builds/{slug}/releases/{version}/manifest

GET /api/v1/launcher/artifacts/{artifact_id}

POST /api/v1/launcher/auth/token
POST /api/v1/launcher/auth/revoke
```

Предусмотреть:

- Проверку прав клиента.
- Доступ к публичным и приватным сборкам.
- Ограничение количества запросов.
- Возможность отзыва токена лаунчера.
- Проверку целостности файлов.
- Поддержку HTTP Range для больших загрузок.
- Логирование загрузок.
- Возможность узнать актуальную версию релиза.

Для лаунчера использовать отдельные ограниченные токены доступа, а не передавать административную браузерную сессию.

Лаунчер должен иметь возможность получить список сборок, запросить манифест, сравнить локальные SHA-256 с серверными и загрузить только отсутствующие или изменённые файлы.

# 8. РАБОЧЕЕ ПРОСТРАНСТВО №2 — NEXUS CLOUD STORAGE

Создать полноценное веб-файлохранилище, физически размещающее файлы на выбранных дисках и в указанных администратором каталогах сервера.

## 8.1. Основная концепция

Пользователь работает с файлами через браузер.

Администратор самостоятельно определяет:

- Диск.
- Каталог хранения.
- Доступность диска.
- Правила использования пространства.
- Разрешённые объёмы хранения.
- Привязку хранилища к рабочим пространствам или пользователям.

Система не должна требовать от пользователя установки клиента на компьютер.

## 8.2. Управление дисками

Создать страницу:

`/system/storage`

Отображать все обнаруженные физические и логические диски сервера.

Информация:

- Буква или точка монтирования.
- Название диска.
- Тип файловой системы.
- Общий объём.
- Использованный объём.
- Свободное место.
- Состояние.
- Подключён / отключён.
- Зарегистрированные каталоги хранения.

Для каждого диска предусмотреть кнопку добавления каталога хранения.

Пример настройки:

```text
Диск: D:\
Название: Storage SSD
Каталог: D:\NexusData\Cloud

Диск: E:\
Название: Archive HDD
Каталог: E:\NexusData\Archive

Диск: F:\
Название: Minecraft Builds
Каталог: F:\NexusData\Builds
```

Для Windows предусмотреть обнаружение букв дисков и доступных каталогов.

Важно: выбор папки на сервере выполняется через защищённый серверный интерфейс управления каталогами. Нельзя полагаться на браузерный `<input type="file">` или `<input type="directory">` для выбора директорий удалённого сервера.

Backend должен:

- Проверять существование каталога.
- Проверять права на запись.
- Проверять свободное пространство.
- Нормализовать и канонизировать путь.
- Проверять символьные ссылки, junctions и другие способы выхода за разрешённый корень.
- Запрещать регистрацию системных и критически важных каталогов.
- Предоставлять файловые операции только внутри зарегистрированных корней.

Ни один пользовательский API-запрос не должен давать возможность произвольно передавать абсолютный путь для чтения, записи или удаления файлов.

## 8.3. Несколько дисков

Обязательно поддержать одновременную работу с несколькими дисками.

Реализовать два режима:

**Ручной режим**
Администратор указывает, какой диск используется для конкретного хранилища, пространства или группы пользователей.

**Автоматический режим**
Система выбирает подходящий зарегистрированный диск по:

- Свободному месту.
- Состоянию.
- Приоритету.
- Действующим ограничениям.

Перед каждой записью проверять достаточность свободного места с учётом заданного резерва.

Один файл должен размещаться целиком в одном зарегистрированном хранилище. Не разбивать обычные файлы между физическими дисками.

Если диск недоступен, не пытаться автоматически перезаписывать данные в другое место без подтверждённого действия или заранее выбранной политики.

Не выполнять автоматическое перемещение уже существующих файлов между дисками.

## 8.4. Движок хранения файлов

Разработать общий низкоуровневый сервис Storage Engine.

Его задачи:

- Сохранение.
- Чтение.
- Удаление.
- Проверка существования.
- Расчёт SHA-256.
- Определение размера.
- Управление объектами.
- Потоковая загрузка и скачивание.
- Работа с несколькими корнями хранения.

Предусмотреть внутреннюю структуру:

```text
NexusData/
├── .nexus/
│   ├── objects/
│   ├── staging/
│   └── quarantine/
```

Физическое расположение определяется внутренним идентификатором объекта.

Оригинальные имена и пользовательская структура папок хранятся в БД как метаданные.

Это необходимо, чтобы избежать коллизий имён, path traversal и раскрытия внутреннего расположения файлов.

При этом пользователь должен видеть привычную структуру директорий в браузере.

Модули Cloud Storage и Minecraft Build Manager используют общий низкоуровневый движок только через контролируемые сервисные интерфейсы.

Для связи объектов между модулями предусмотреть отдельные ссылки и счётчик ссылок на физический объект. Удаление пользовательской записи не должно уничтожать файл, если он ещё используется опубликованной сборкой или другим разрешённым владельцем.

Не реализовывать автоматическое дублирование одного и того же файла между каталогами.

## 8.5. Файловый менеджер

Основной интерфейс должен напоминать современное облачное хранилище.

Слева:

- Все файлы.
- Мои файлы.
- Недавние.
- Избранное.
- Общий доступ.
- Корзина.

В верхней части:

- Хлебные крошки.
- Поиск.
- Сортировка.
- Переключение вида.
- Кнопка загрузки.
- Кнопка создания папки.

Основная область:

- Таблица или сетка.
- Название.
- Тип.
- Размер.
- Дата изменения.
- Владелец.
- Статус.

Два режима просмотра:

- Таблица.
- Сетка.

Поддержать:

- Создание папок.
- Загрузку файлов.
- Множественную загрузку.
- Загрузку папок.
- Перемещение.
- Переименование.
- Удаление.
- Восстановление.
- Перемещение в корзину.
- Скачивание.
- Массовые операции.
- Поиск.
- Сортировку по названию, размеру и дате.
- Фильтры по типу.
- Избранное.

- Повтор после ошибки.
- Прогресс для каждого файла.
- Общий прогресс очереди.
- Скорость передачи.
- Оставшееся время, если его можно достоверно рассчитать.

**Использовать возобновляемую загрузку по протоколу tus 1.0.0 либо собственную документированную реализацию с аналогичной надёжностью.**

Frontend может использовать tus-js-client, backend реализует совместимый HTTP-интерфейс.

Необходимые возможности:

- Создание upload session.
- Определение размера.
- Получение текущего смещения.
- Передача чанков.

Поддерживать большие файлы и крупные наборы данных. Конкретный максимальный размер задаётся настройками сервера и правами пользователя.

Прогресс передачи получать из реального количества переданных байтов, а не имитировать анимацией.

## 8.7. Особая обработка одинаковых имён файлов

Реализовать надёжную систему замены существующих файлов.

Если в текущей папке существует файл с таким именем:

- Не заменять его автоматически.
- Вернуть HTTP 409 с кодом `FILE_NAME_CONFLICT`.
- Передать ID существующего файла.
- Показать в интерфейсе выбор: отмена, переименование, замена.

При подтверждении замены:

1. Создать временную загрузку нового содержимого.
2. Сохранить существующий файл без изменений.
3. Полностью принять новые данные.
4. Проверить размер и SHA-256.
5. Подготовить новый объект.
6. Атомарно переключить запись на новый объект.
7. Только после успешного завершения освободить старую ссылку, если больше нет других владельцев.

Использовать транзакционную логику, состояния операции и Idempotency-Key для защиты от повторных запросов.

При любой ошибке или отключении сервера исходный файл должен оставаться доступным.

Не допускать частичного затирания старого файла.

- Выдавать файлы клиентскому лаунчеру.
- Продолжать загрузки после сетевых разрывов.
- Работать без неконтролируемого роста RAM.

Конкретную пропускную способность определять нагрузочными тестами на целевом оборудовании. Не обещать скорость, которую не подтверждают измерения.

# 17. КРИТЕРИИ ПРИЁМКИ

Система считается реализованной, если выполнены следующие требования.

**Общая платформа**

- Сервер запускается на Rust.
- Веб-интерфейс открывается из браузера.
- Страница авторизации работает.
- Пользователи и права доступа работают.
- Рабочие пространства разделены.
- Главная страница соответствует дизайну референсов.
- 3D-фон работает и настраивается.

**Minecraft Build Manager**

- Можно создать сборку.
- Можно выбрать Minecraft и загрузчик.
- Можно загрузить моды, конфиги, текстурпаки и шейдеры.
- Можно настроить структуру файлов.
- Можно сформировать корректный манифест.
- Можно создать опубликованный релиз.
- Лаунчер может получить список сборок, манифест и файлы.
- SHA-256 совпадает у сервера и клиента.

**Cloud Storage**

- Можно настроить несколько дисков.
- Можно указать каталоги хранения.
- Файлы сохраняются физически в зарегистрированных корнях.
- Работают папки и операции с файлами.
- Большие загрузки возобновляются.
- Скачивание поддерживает Range.
- Предпросмотр поддерживаемых форматов работает.
- Неуспешная замена не повреждает исходный файл.
- Пользователи не получают доступ к чужим файлам без разрешений.

**System Management**

- Можно создавать и управлять пользователями.
- Работают права по отдельным модулям.
- Отображаются реальные показатели сервера.
- Графики получают данные с backend.
- Журнал событий фиксирует важные операции.
- Фоновые задачи управляются через интерфейс.

**Надёжность**

- Нет неконтролируемого расхода RAM при больших загрузках.
- Нет потери исходных данных при сетевом обрыве.
- Нет возможности выйти за зарегистрированный каталог хранения.
- Перезапуск сервера не приводит к повреждению опубликованных сборок.
- После неудачной операции файлы остаются в согласованном состоянии.

# 18. ОБЯЗАТЕЛЬНЫЕ ПРАВИЛА РАЗРАБОТКИ

1. Не использовать фиктивные данные вместо настоящего API.
2. Не делать декоративные кнопки без работающих действий.
3. Не создавать графики с подставными системными показателями.
4. Не имитировать прогресс загрузки.
5. Не хранить файлы целиком в RAM.
6. Не использовать произвольные пути файловой системы из запросов пользователя.
7. Не смешивать функциональность двух рабочих пространств.
8. Не хранить большие бинарные данные в PostgreSQL.
9. Не использовать абсолютные серверные пути в манифестах.
10. Не делать автоматическую замену файлов без подтверждения.
11. Не удалять физические данные без проверки всех ссылок.
12. Не блокировать работу приложения длительными файловыми операциями.
13. Не создавать бесконтрольные фоновые процессы.
14. Не оставлять TODO вместо обязательных функций.
15. Не скрывать ошибки API от пользователя.
16. Не менять архитектуру всего проекта ради локального исправления без необходимости.
17. Не создавать несколько реализаций одной и той же функции в разных модулях.
18. Все новые API должны иметь документированные контракты.
19. Все важные операции должны иметь обработку ошибок и проверяемый результат.
20. Все этапы должны завершаться сборкой и тестированием.
