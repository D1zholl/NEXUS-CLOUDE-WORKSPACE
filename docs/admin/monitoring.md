# Модули, задачи, мониторинг, журнал и настройки

> Часть руководства администратора NEXUS WORKSPACE. Полный индекс — [ADMIN_GUIDE.md](../ADMIN_GUIDE.md).

## 5. Отключение модулей

**Система → Состояние → Модули.** Доступно с `system.settings.manage`.
Переключатели `Minecraft Build Manager` и `NEXUS Cloud Storage` действуют
немедленно.

Что происходит:

* модуль исчезает из боковой навигации у всех пользователей после
  обновления страницы (сессия обновляется при следующем входе или вызове
  `/auth/me`);
* API модуля отвечает `403 MODULE_DISABLED` (для `/api/v1/launcher` —
  `404`, чтобы не раскрывать состояние внешнему клиенту);
* данные не удаляются: файлы, сборки, релизы и настройки остаются;
* публичные ссылки `/api/v1/public/shares/...` продолжают работать;
* событие `module.toggled` пишется в журнал;
* включение возвращает доступ без перезапуска.

Отключение `minecraft` также закрывает Launcher API (`/launcher`) и
административные маршруты лаунчера (`/admin/launcher`). Отключение `cloud`
закрывает `/cloud`, но не публичные ссылки.

⚠ Отключение модуля не останавливает уже выполняющиеся фоновые задачи и не
завершает сессии. Не используйте его как «мягкое удаление» — для запрета
доступа отключайте пользователей или снимайте права.

## 6. Фоновые задачи

Две страницы:

* **Система → Фоновые задачи** — очередь, счётчики, фильтры, пауза,
  продолжение и отмена;
* **Система → Обслуживание** — кнопки запуска и краткая история.

Просмотр доступен с `system.view`, запуск, пауза, продолжение и отмена — с
`system.jobs.manage`.

### 6.1. Типы задач

| Кнопка | Тип | Что делает |
|---|---|---|
| Проверить целостность | `system.storage.check` | проверяет тома (при смене состояния публикует `storage.volume.updated`) и сверяет объекты `committed` с диском, помечает отсутствующие/несовпадающие как `missing` |
| Сверка SHA-256 (только API) | `system.objects.verify` | проверяет размер и SHA-256 объектов; `mode=full` — все, `mode=sample` — выборка (`samplePercent`, по умолчанию 10 %) |
| Очистить временные загрузки | `system.uploads.cleanup` | удаляет просроченные сессии Cloud и Minecraft (владельцу уходит `upload.failed` с кодом `UPLOAD_EXPIRED`), staging-файлы и старые ZIP-архивы |
| Удалить истёкшие ссылки | `system.shares.cleanup` | удаляет ссылки и токены лаунчера через 30 дней после истечения/отзыва |
| Автоочистка корзины | `system.trash.cleanup` | удаляет записи корзины старше `limits.trash_retention_days`, освобождает ссылки и сохраняет объекты, используемые другими модулями; пишет аудит `cloud.trash.cleaned` |
| Очистить старые метрики | `system.metrics.prune` | удаляет метрики старше 7 дней и завершённые задачи старше 30 дней |

### 6.2. Пауза, продолжение и ограничения

* Планировщик опрашивает очередь каждые 1,5 с и атомарно захватывает задачи
  (`FOR UPDATE SKIP LOCKED`). Одновременно выполняется не более
  `jobs.max_concurrent` задач (по умолчанию 2); лимит применяется без
  перезапуска.
* При старте сервера незавершённые `running` возвращаются в `pending`,
  причина остаётся в `error`. При остановке новые задачи не берутся, а
  текущие получают `cancel_requested`.
* Пауза `POST /jobs/{id}/pause` (`system.jobs.manage`): ожидающая задача
  переходит в `paused` сразу, выполняющаяся — после текущей единицы работы
  (`pause_requested` → `paused`, `paused_at`) и освобождает слот планировщика.
* Продолжение `POST /jobs/{id}/resume` возвращает `paused` → `pending`,
  сбрасывает флаг и время паузы. Отмена задачи на паузе применяется сразу.
* Отмена кооперативная: задача проверяет флаг между объектами. Уже
  обработанные файлы остаются как есть.
* Итоговая статистика пишется в `background_jobs.result`; ошибки — в `error`
  и дублируются в аудите событием `job.failed`. В UI видны статус, прогресс,
  длительность, причина недоступности действий и текст ошибки; список
  обновляется по realtime и опросом.

### 6.3. Регламент

| Периодичность | Действие |
|---|---|
| Ежедневно | проверить «С ошибкой» и свободное место |
| Еженедельно | «Очистить временные загрузки», «Удалить истёкшие ссылки» и «Автоочистка корзины» |
| Ежемесячно | «Проверить целостность» вне часов нагрузки |
| После восстановления/переезда | «Проверить целостность» обязательно |

Проверка целостности на большом объёме читает метаданные всех объектов и
может идти долго; прогресс виден в столбце «Прогресс» и обновляется через
WebSocket.

## 7. Мониторинг

### 7.1. Что показывает

**Система → Мониторинг** (данные требуют `system.monitoring.view`):

* процессор: общая загрузка, число ядер, load average, загрузка по ядрам;
* память: использовано/всего, процесс NEXUS, swap;
* диски: все обнаруженные устройства, свободное место, заполнение;
* сеть: входящая/исходящая скорость по всем интерфейсам;
* приложение: RPS, средняя задержка API, ошибки за минуту, сессии,
  активные пользователи, задачи в очереди, активные загрузки, состояние БД,
  хост и ОС;
* модули: сборки/публикации/файлы/релизы Minecraft, файлы и ссылки Cloud,
  объекты и недоступные объекты хранилища, ошибки за 24 часа, скачивания
  лаунчера.

История: `5 минут`, `15 минут`, `1 час`, `24 часа`, `7 дней` с шагом
10/20/60/600/3600 секунд. Кнопка «Автообновление: вкл/выкл» останавливает и
возобновляет опрос страницы.

Источники данных реальные: `sysinfo`, счётчики процесса, таблицы
PostgreSQL. Декоративных значений нет.

### 7.2. Частота и хранение

| Параметр | Значение |
|---|---|
| Снимок в памяти | каждые 2 секунды |
| Запись истории | каждые 10 секунд |
| Очистка истории | старше 7 дней, при каждой записи |
| Realtime-событие `system.metrics.updated` | каждые 5 секунд при наличии клиентов |
| Обновление страницы «Мониторинг» | 3 секунды (текущие), 10 секунд (история) |
| Обновление «Состояние системы» | 15 секунд |

### 7.3. Диагностика

* Порог предупреждения в UI: CPU > 85%, память > 88%, диск > 90%.
* Автоматических уведомлений и алертов нет. Для внешнего контроля
  используйте `GET /api/v1/health`: он возвращает `200` и
  `"status": "degraded"` при недоступной БД, поэтому проверяйте тело
  ответа, а не только код.
* После первого запуска (или очистки метрик) история пуста и заполняется в
  течение 10 секунд; при перезапуске ранее записанные точки сохраняются.
* Значения CPU и сети зависят от интервала опроса: первый снимок может
  показывать 0.

## 8. Журнал и логи

### 8.1. Журнал действий

**Система → Журнал событий** (`system.view`). Столбцы: время, тип события,
актор, объект, результат, IP, детали JSON. Фильтр по типу, 25 записей на
страницу, обновление вручную.

Основные события:

* `auth.login.success`, `auth.login.failed`, `auth.logout`,
  `auth.password.changed`, `auth.sessions.revoked`;
* `user.created/updated/deleted/password.reset/unlocked/sessions.revoked`;
* `role.created/updated/deleted`;
* `module.toggled`;
* `settings.user.updated`, `settings.system.updated`;
* `storage.volume.*`;
* `jobs.maintenance_started`, `jobs.pause_requested`, `jobs.resumed`,
  `jobs.cancel_requested`, `job.failed`.

В журнал не попадают пароли, токены, содержимое файлов и секреты. Детали
события — только идентификаторы, имена и безопасные параметры.

⚠ Автоматической очистки `audit_events` нет. Журнал растёт постоянно и
входит в резервную копию БД. Планируйте его объём и архивирование.

### 8.2. Логи приложения

Логи пишутся в stderr и, если задан `NEXUS_LOG_DIR`, в файл
`NEXUS_LOG_FILE` (по умолчанию `nexus.log`).

* При старте текущий файл переименовывается в
  `<имя>.<ГГГГММДД-ЧЧММСС>`; хранятся последние `NEXUS_LOG_KEEP` архивов
  (по умолчанию 7).
* Ротация выполняется **только при запуске**; в течение работы файл растёт.
* Уровень задаётся `RUST_LOG` (по умолчанию
  `nexus=info,tower_http=info,sqlx=warn`).
* Windows: `C:\NexusWorkspace\logs`.

При разборе инцидента сначала смотрите журнал действий (кто и что сделал),
затем лог приложения (ошибка и стек), затем события ОС/PostgreSQL.

## 9. Системные настройки

### 9.1. Страницы и права

| Страница | Ключи | Право |
|---|---|---|
| Общие настройки | параллельные загрузки, задачи, качество фона | `system.settings.manage` |
| Ограничения ресурсов | размеры, TTL, квоты, задачи | `system.settings.manage` |
| Сеть | CORS, доверие прокси | `system.settings.manage` |
| Безопасность | сессии, блокировки, длина пароля | `system.settings.manage` |

Каждое значение проверяется по реестру
`backend/src/system/settings_catalog.rs`: тип, диапазон, допустимые
варианты. Неизвестный ключ → `422 UNKNOWN_SETTING`; неверное значение →
`422 VALIDATION_ERROR`. Изменение пишется в журнал
(`settings.system.updated`).

Ключи с `requiresRestart` показаны **только для чтения** с бейджем
«после перезапуска»: интерфейс не создаёт видимость изменения, которое не
вступит в силу. Если сохранённое значение отличается от действующего,
рядом появляется бейдж «ожидает перезапуска» и подсказка с обоими
значениями.

Кэш настроек — 10 секунд, но при сохранении он инвалидируется: изменённое
значение применяется сразу, без ожидания TTL. Аудит
`settings.system.updated` содержит `{key, old, new}`; значения настроек
секретами не являются.

Интерфейс показывает **эффективные** значения: `GET /system/settings`
возвращает `effective` рядом с сохранёнными `values`. Если ключ ещё не
сохранялся, отображается не минимальное значение реестра, а действующее
значение из `nexus.toml` или встроенное (например, 10 ГБ для
`limits.max_upload_mb` и 2 для `jobs.max_concurrent`).

### 9.2. Что действует в этой сборке

| Ключ | Диапазон | При отсутствии | Фактическое применение |
|---|---|---|---|
| `limits.max_upload_mb` | 1–102400 | 10 ГБ из `nexus.toml` | ✅ новые загрузки Cloud и Minecraft; эффективное значение в `/cloud/config` и `/minecraft/uploads/config` |
| `limits.chunk_max_mb` | 1–256 | 64 МБ | ✅ обработчики чанков, `/uploads/config`, статус сессии |
| `limits.upload_ttl_hours` | 1–720 | 24 ч | ✅ новые сессии загрузки |
| `limits.share_ttl_hours` | 1–8760 | 168 ч | ✅ срок новой ссылки, если он не задан явно; значение показано в форме ссылки |
| `limits.export_ttl_hours` | 1–720 | 6 ч | ✅ очистка готовых ZIP-архивов и подпись срока хранения в списке архивов |
| `limits.trash_retention_days` | 1–3650 | 30 дней | ✅ задача `system.trash.cleanup`; дата удаления видна в корзине и на `/system/limits` |
| `limits.quota_cloud_gb` | 1–1 000 000 | 50 ГБ | ✅ обновляет `quota_defaults` без перезапуска |
| `limits.quota_minecraft_gb` | 1–1 000 000 | 100 ГБ | ✅ обновляет `quota_defaults` без перезапуска |
| `jobs.max_concurrent` | 1–8 | 2 | ✅ планировщик применяет лимит на каждом цикле (1,5 с) |
| `cloud.upload.concurrency` | 1–6 | 3 | ✅ `/cloud/config` → очередь загрузок браузера |
| `security.session_ttl_hours` | 1–720 | 24 ч | ✅ новые сессии и скользящее продление при активности |
| `security.login_max_failures` | 3–50 | 10 в БД | ✅ порог блокировки учётной записи (лимитер 5/15 мин остаётся отдельно) |
| `security.password_min_length` | 8–64 | 12 | ✅ создание/смена/сброс пароля через API и подсказки в UI; CLI — из конфига, по умолчанию 12 |
| `network.allowed_origins` | JSON-массив | `[]` (same-origin) | ✅ применяется при старте службы: переопределяет `NEXUS_CORS_ORIGINS` / `nexus.toml` |
| `network.trust_proxy` | `true/false` | `false` | ✅ применяется при старте службы: переопределяет `NEXUS_TRUST_PROXY` / `nexus.toml` |
| `appearance.background.quality` | `auto/high/eco` | `auto` | ✅ fallback-качество для пользователей без личных настроек |
| `appearance.background.defaults` | JSON-объект | встроенные значения | ✅ fallback с дополнением недостающих полей |

Все 17 ключей реестра применяются: 15 — сразу после сохранения, два
`network.*` — при следующем старте службы (бейдж «после перезапуска»).
`jobs.max_concurrent` планировщик читает на каждом цикле, поэтому лимит
меняется без перезапуска и сразу виден в `/jobs` (`maxConcurrent`).

Практические следствия новых ключей:

* `limits.trash_retention_days` задаёт срок жизни корзины. В интерфейсе
  корзины у каждой записи показана дата удаления (`trashedAt + срок`).
  Фактическое удаление выполняет задача `system.trash.cleanup`
  (`POST /jobs/maintenance` с `kind = cleanup_trash`): она освобождает
  облачные ссылки и удаляет объект только при отсутствии других ссылок.
  Запускайте задачу по расписанию; повторный запуск безопасен.
* `limits.share_ttl_hours` подставляет срок в форму ссылки. Режим «Только для
  авторизованных» требует cookie-сессию даже при наличии пароля.
* `limits.export_ttl_hours` управляет сроком хранения ZIP. Владелец может
  удалить архив кнопкой «Удалить архив» (`DELETE /cloud/exports/{id}`), пока
  задача завершена или завершилась ошибкой; после удаления скачивание — 404.

### 9.3. Сетевые настройки

`network.allowed_origins` и `network.trust_proxy` в интерфейсе доступны
только для чтения. Значения хранятся в `system_settings` и применяются в
`serve()` после подключения к БД, но **до** создания `AppState` и сборки
маршрутизатора. Поэтому:

1. Сохраните значение через API (с правом `system.settings.manage`):

```powershell
# Cookie-сессия администратора и CSRF-токен обязательны.
Invoke-RestMethod -Method Put `
  -Uri https://nexus.example.com/api/v1/system/settings/network.allowed_origins `
  -Headers @{ 'X-CSRF-Token' = $csrf } `
  -ContentType 'application/json' `
  -Body '["https://nexus.example.com","https://admin.example.com"]'
```

2. Перезапустите службу (`Restart-Service NEXUS` или
   `systemctl restart nexus`). До перезапуска CORS продолжает отдавать
   старый список, после — новый.

Если записи в `system_settings` нет, действуют значения из конфигурации:

```dotenv
NEXUS_CORS_ORIGINS=https://nexus.example.com,https://admin.example.com
NEXUS_TRUST_PROXY=true
```

Запись в `system_settings` имеет приоритет над `.env`/`nexus.toml`:
удалите ключ из таблицы, чтобы вернуться к конфигурации.

`trust_proxy=true` допустим **только** за доверенным обратным прокси:
иначе клиент подделает `X-Forwarded-For` и обойдёт лимиты входа. Хост и
порт (`NEXUS_HOST`, `NEXUS_PORT`) также меняются только в конфигурации с
перезапуском.

⚠ `install-windows.ps1` записывает `NEXUS_TRUST_PROXY=true` независимо от
того, есть ли прокси. При прямом доступе к `:8080` исправьте значение на
`false` и перезапустите службу.

### 9.4. Порядок изменения

1. Сделайте резервную копию (раздел 10).
2. Измените один ключ.
3. Проверьте эффект: загрузку, сессию, мониторинг.
4. Зафиксируйте изменение в журнале эксплуатации.
5. Для `requiresRestart` перезапустите службу и повторите проверку.
