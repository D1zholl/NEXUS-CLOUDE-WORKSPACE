# Манифест релиза Minecraft (schema 1.0)

Документ описывает формат манифеста, который получает лаунчер для сборки
Minecraft. Источник истины по полям — `backend/src/minecraft/manifests.rs`;
машиночитаемый контракт — [`schemas/manifest-1.0.json`](schemas/manifest-1.0.json)
(JSON Schema 2020-12). Связанные документы: [`API.md`](API.md),
[`ARCHITECTURE.md`](ARCHITECTURE.md).

---

## 1. Назначение и версия

* Манифест — снимок **опубликованного релиза**, а не текущего состояния
  сборки. Он строится из таблиц `minecraft_releases` и
  `minecraft_release_files`.
* `schema_version` — версия **формата манифеста**, а не версия сборки и не
  версия API. Для этого документа она строго равна `"1.0"`.
* Версия API (`/api/v1`) и версия продукта (`0.1.0` → `1.0.0`) меняются
  независимо от `schema_version`.
* Обратно совместимые дополнения (новые необязательные поля) не меняют
  `schema_version`. Несовместимое изменение структуры требует
  `schema_version: "2.0"` и нового файла схемы.

Эндпоинты, отдающие манифест:

| Метод | Путь | Доступ |
|---|---|---|
| `GET` | `/api/v1/launcher/builds/{slug}/latest/manifest` | токен лаунчера, scope `launcher.catalog` |
| `GET` | `/api/v1/launcher/builds/{slug}/releases/{version}/manifest` | токен лаунчера, scope `launcher.catalog` |
| `GET` | `/api/v1/launcher/builds/{slug}/icon` | токен лаунчера, scope `launcher.catalog` |
| `GET` | `/api/v1/minecraft/builds/{id}/releases/{release_id}/manifest` | браузерная сессия, право `minecraft.view` |

Публикация релиза сохраняет манифест в `minecraft_releases.manifest`.
Повторный запрос опубликованного релиза возвращает сохранённый документ,
а не пересобирает его из текущей сборки.

## 2. Структура верхнего уровня

```jsonc
{
  "schema_version": "1.0",
  "build":       { /* снимок сборки */ },
  "minecraft":   { /* версия игры */ },
  "loader":      { /* загрузчик */ },
  "java":        { /* требования Java */ },
  "icon":        { /* необязательно, если задана иконка сборки */ },
  "files":       [ /* артефакты релиза */ ]
}
```

| Поле | Тип | Обязательно | Правило |
|---|---|---|---|
| `schema_version` | string | да | ровно `"1.0"` |
| `build` | object | да | см. §3 |
| `minecraft` | object | да | см. §3 |
| `loader` | object | да | см. §3 |
| `java` | object | да | см. §3 |
| `icon` | object | нет | см. §6; добавляется, если у сборки задана иконка |
| `files` | array | да | см. §4; порядок детерминирован |

Других полей в schema 1.0 нет: схема использует
`"additionalProperties": false`. Клиент лаунчера обязан **игнорировать
неизвестные поля**, чтобы манифест, созданный более новой версией сервера,
не ломал установку.

## 3. Блоки `build`, `minecraft`, `loader`, `java`

### 3.1. `build`

| Поле | Тип | Ограничения | Источник |
|---|---|---|---|
| `id` | string (UUID) | нижний регистр, 36 символов | `minecraft_builds.id` |
| `slug` | string | 2–64, `^[a-z0-9]+(-[a-z0-9]+)*$` | `minecraft_builds.slug` |
| `name` | string | 2–96 символов | `minecraft_builds.name` |
| `release` | string | 1–32, `[A-Za-z0-9._+-]` | `minecraft_releases.version` |
| `changelog` | string | может быть пустым | `minecraft_releases.changelog` |

`build.release` — версия релиза (`1.0.0`, `1.0.0-beta2`). Она уникальна в
пределах сборки и не совпадает с `schema_version`.

### 3.2. `minecraft`

| Поле | Тип | Ограничения |
|---|---|---|
| `version` | string | до 32 символов; пустая строка допустима, если версия не задана |

### 3.3. `loader`

| Поле | Тип | Ограничения |
|---|---|---|
| `type` | string | `vanilla`, `fabric`, `forge`, `neoforge`, `quilt` |
| `version` | string | для `vanilla` может быть пустой; для остальных обязательна при создании сборки |

### 3.4. `java`

| Поле | Тип | Ограничения |
|---|---|---|
| `major` | integer | 8–30 |
| `min` | integer | 8–30, не больше `major` |
| `notes` | string | может быть пустой |

## 4. Файлы релиза

Каждый элемент `files[]` описывает один артефакт:

| Поле | Тип | Обязательно | Правило |
|---|---|---|---|
| `id` | string (UUID) | да | идентификатор артефакта релиза |
| `path` | string | да | относительный путь внутри сборки, 1–512 символов |
| `category` | string | да | `mods`, `config`, `resourcepacks`, `shaderpacks`, `scripts`, `overrides`, `other` |
| `side` | string | да | `client`, `server`, `both` |
| `required` | boolean | да | обязателен ли файл |
| `size` | integer | да | точный размер в байтах, `>= 0` |
| `sha256` | string | да | 64 hex-символа в нижнем регистре |
| `download_url` | string | да | относительный URL вида `/api/v1/launcher/artifacts/{id}` |

В манифест попадают только включённые файлы (`enabled = true`). Папки в
`files[]` не попадают: структура каталогов восстанавливается из `path`.

### 4.1. Правила относительных путей

Путь хранится и сравнивается в нормализованном виде (см.
`backend/src/minecraft/validation.rs`):

* разделитель — только прямой слэш `/`; обратный слэш в готовом манифесте
  отклоняется, а не нормализуется (при загрузке он приводится к `/`);
* Unicode приводится к NFC; готовый манифест с путём не в NFC отклоняется;
* запрещены ведущий `/`, буква диска (`C:`), UNC-пути (`//server/share`),
  ADS-двоеточия (`file.jar:stream`);
* запрещены сегменты `.` и `..`;
* запрещены управляющие символы;
* запрещены символы, недопустимые в Windows: `< > : " | ? *`;
* сегмент не может заканчиваться точкой или пробелом;
* запрещены зарезервированные имена Windows (`CON`, `PRN`, `AUX`, `NUL`,
  `COM1`–`COM9`, `LPT1`–`LPT9`) независимо от расширения;
* длина пути — до 512 символов, сегмента — до 128;
* уникальность путей в сборке проверяется без учёта регистра и нормализации
  Unicode, чтобы установка на Windows не перезаписывала файлы. Проверка
  выполняется и при публикации релиза, и при отдаче сохранённого манифеста:
  снимок с коллизией (`Mods/A.jar` и `mods/a.jar`) не публикуется.

### 4.2. SHA-256, размер и `download_url`

* `sha256` считается потоково по фактическому содержимому объекта при
  фиксации загрузки (`storage/hashing.rs`); в манифест попадает значение из
  `minecraft_release_files.sha256`.
* `size` — точный размер принятого файла. При завершении загрузки сервер
  сверяет полученное число байт с заявленным и отклоняет расхождение.
* `download_url` всегда относительный. Абсолютные URL, схемы (`http:`,
  `file:`), буквы дисков и UNC-пути запрещены и проверяются
  `validate_manifest`. Клиент резолвит URL относительно базового адреса
  сервера и передаёт свой токен лаунчера.
* Скачивание артефакта требует scope `launcher.artifacts`, учитывает лимиты
  частоты и поддерживает `Range`.

## 5. Детерминированность

Манифест одного и того же релиза должен быть идентичен при повторной
генерации:

* файлы сортируются **байтовым сравнением** `path` (`as_bytes()`), а не
  `lower(path)` и не средствами СУБД: результат не зависит от локали,
  коллации PostgreSQL и регистра/нормализации конкретной ОС;
* байтовый порядок стабилен для ASCII и не-ASCII (NFC): сравнение идёт по
  UTF-8, а не по правилам языка; `id` артефакта служит детерминированным
  tie-breaker;
* путь в манифесте — только относительный, с прямыми слэшами `/` и в NFC;
  обратный слэш и NFD отклоняются, а не нормализуются на выдаче;
* в манифесте нет времени генерации, случайных идентификаторов и счётчиков;
* `id` файлов — стабильные идентификаторы снимка релиза;
* `icon.sha256` берётся из `storage_objects.sha256`; при неизменной иконке
  повторная генерация даёт тот же блок `icon`;
* порядок загрузки файлов в сборку не влияет на порядок и содержимое
  `files[]`;
* повторная публикация уже опубликованного релиза возвращает сохранённый
  манифест.

Проверки: `backend/tests/minecraft_tests.rs` (двойная генерация, порядок
загрузки, байтовая сортировка и Unicode NFC) и
`backend/tests/manifest_schema_tests.rs` (валидация реально сгенерированного
манифеста по JSON Schema).

## 6. Иконка сборки

Поле `icon` необязательное: генератор добавляет его, если у сборки задана
иконка и объект хранения находится в состоянии `committed`.

```jsonc
{
  "icon": {
    "url": "/api/v1/launcher/builds/create-expert/icon",
    "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  }
}
```

Правила:

* `url` — относительный путь именно этой сборки
  (`/api/v1/launcher/builds/{slug}/icon`); абсолютные URL и серверные пути
  запрещены;
* `sha256` — SHA-256 фактически отдаваемого изображения из
  `storage_objects.sha256`, 64 hex-символа в нижнем регистре;
* поле аддитивное: `schema_version` остаётся `"1.0"`; отсутствие иконки не
  делает манифест невалидным;
* `content_type` в `icon` не дублируется: клиент получает его из заголовка
  `Content-Type` при скачивании.

Эндпоинт `GET /api/v1/launcher/builds/{slug}/icon`:

* требует токен лаунчера со scope `launcher.catalog`;
* отдаёт иконку только для опубликованной сборки, которая публична или
  принадлежит владельцу токена; чужой токен получает `404`, а не `403`,
  чтобы не раскрывать существование приватной сборки;
* определяет `Content-Type` по сигнатуре содержимого (`image/png`,
  `image/jpeg`, `image/webp`), а не по расширению или заявленному типу;
* возвращает `ETag` с SHA-256 и `Cache-Control: private, max-age=60`;
* учитывает лимит частоты и отдаёт заголовки `X-RateLimit-*`.

Иконки, загруженные до включения G1, попадают в уже опубликованные релизы
только через аддитивную задачу `system.manifests.regenerate` (§7).

## 7. Неизменяемость опубликованного релиза

* При создании релиза строки `minecraft_build_files` копируются в
  `minecraft_release_files`; дальнейшие изменения сборки не затрагивают
  снимок.
* Снимок увеличивает `storage_objects.ref_count`, поэтому объекты нельзя
  удалить, пока на них ссылается опубликованный релиз.
* Публикация выполняет проверку сборки, строит манифест, валидирует его и
  сохраняет в `minecraft_releases.manifest` в одной транзакции.
* Опубликованный релиз нельзя переписать «на месте». Новая версия — новый
  релиз; переключение текущей версии (откат) меняет
  `minecraft_builds.current_release_id`, но не содержимое релиза.
* Удаление сборки с опубликованными релизами запрещено
  (`BUILD_HAS_PUBLISHED_RELEASES`).
* Допустимая регенерация — только аддитивная (добавление `icon`) через явную
  задачу `system.manifests.regenerate` с записью в аудит; она не меняет
  `build`, `minecraft`, `loader`, `java` и `path`/`size`/`sha256` файлов.
* Задача обходит опубликованные и устаревшие (`deprecated`) релизы в
  детерминированном порядке, пересобирает манифест из снимка и сравнивает
  его с сохранённым без поля `icon`. Совпавшие релизы не перезаписываются.
  Порядок `files` может нормализоваться к байтовой сортировке G3 — это не
  меняет сами файлы. Если различается что-то кроме `icon` и порядка
  `files`, релиз пропускается и попадает в `result.skippedReleases`; его
  документ остаётся неизменным.
* Каждое фактическое изменение пишет событие аудита
  `minecraft.manifest.regenerated` с `releaseId`, `buildId` и признаком
  наличия иконки. Повторный запуск идемпотентен.

## 8. Delta-обновления (только описание будущего)

Delta-обновления **не реализованы** и полей в коде нет. Это задел на будущее
(K6), а не часть schema 1.0.

Предполагаемая форма (не валидируется текущей схемой):

```jsonc
{
  "files": [
    {
      "path": "mods/example.jar",
      "size": 1048576,
      "sha256": "…64 hex…",
      "download_url": "/api/v1/launcher/artifacts/…",
      "delta": {
        "from_sha256": "…64 hex…",
        "algorithm": "zstd-patch",
        "size": 131072,
        "sha256": "…64 hex…",
        "url": "/api/v1/launcher/artifacts/…"
      }
    }
  ]
}
```

Правила совместимости, если delta будет принята:

* поле `delta` — необязательное и аддитивное; клиент, не знающий о нём,
  скачивает полный файл по `download_url`;
* сервер обязан всегда предоставлять полный файл как fallback;
* итоговый файл после применения патча проверяется по `size` и `sha256`
  полного файла; несовпадение — ошибка, а не «частичный успех»;
* патч проверяется собственными `size`/`sha256`;
* `schema_version` повышается только при несовместимом изменении; при
  аддитивном поле остаётся `1.0`, а файл схемы дополняется;
* до появления кода поля `delta` в манифесте быть не должно — «мёртвые»
  поля запрещены правилами разработки.

### 8.1. Матрица совместимости

| Сервер \ клиент | Старый клиент (schema 1.0 без delta) | Новый клиент (понимает delta) |
|---|---|---|
| **Старый сервер (1.0, без `delta`)** | полная совместимость | клиент видит отсутствие `delta` и скачивает полный файл |
| **Новый сервер (1.0, `delta` добавлен аддитивно)** | игнорирует неизвестное поле, скачивает `download_url` | использует `delta`, при ошибке/несовпадении SHA — полный файл |
| **Несовместимое изменение (например, `files` стал объектом)** | не поддерживается | требуется новый `schema_version` |

Правила для будущей реализации:

1. `schema_version` остаётся `"1.0"` до первого несовместимого изменения;
   добавление `delta` — аддитивное изменение, версия не меняется.
2. JSON Schema `docs/schemas/manifest-1.0.json` сохраняет
   `additionalProperties: false`: пока сервер не генерирует `delta`, схема
   отвергает это поле. Вместе с реализацией в схему добавляется опциональное
   свойство и расширяются тесты `manifest_schema_tests`.
3. Генератор манифеста не пишет `delta` для релизов, где патч не построен;
   отсутствие поля — норма, а не ошибка.
4. Клиент обязан уметь скачать полный файл всегда: `delta` — оптимизация
   трафика, а не обязательный путь.
5. Удаление или переименование существующих полей — несовместимое изменение;
   оно требует повышения `schema_version` и нового файла схемы.

В коде 1.0 полей `delta` нет: это только документация и задел (K6).

## 10. Проверка и приёмка

Два независимых уровня:

1. **Runtime** — `manifests::validate_manifest` перед сохранением и
   публикацией: версия схемы, наличие `build.slug`, `build.release`,
   списка файлов, допустимость пути, формат SHA-256, неотрицательный
   размер, отсутствие абсолютных путей в `download_url`.
2. **Контракт/схема** — `backend/tests/manifest_schema_tests.rs`:

   * генерирует манифест через реальный `build_manifest` на тестовой БД;
   * валидирует его библиотекой JSON Schema по
     `docs/schemas/manifest-1.0.json`;
   * извлекает все блоки ` ```json ` из этого документа и проверяет, что
     примеры соответствуют схеме;
   * проверяет, что схема действительно отвергает манифест с отсутствующим
     SHA-256 или абсолютным `download_url`;
   * проверяет, что `icon` добавляется только этой сборке, `sha256` совпадает
     с `storage_objects`, а чужой токен не получает иконку приватной сборки
     (интеграционные тесты лаунчера).

Изменение полей манифеста без обновления этого документа и схемы считается
регрессией контракта.

## 11. Отдельный манифест для MyLauncher

Внутренний манифест `schema_version: "1.0"` выше и манифест MyLauncher —
**разные документы**. Клиент не читает `schema_version`, `download_url` и
`build`; его парсер требует `manifestVersion: 1` и относительный
`/api/files/sha256:{hex}`. Полный контракт и таблица отличий:
[`LAUNCHER_CONTRACT.md`](LAUNCHER_CONTRACT.md). Схема:
[`schemas/launcher-manifest-1.json`](schemas/launcher-manifest-1.json).

Публичные endpoints (без токена, как требует stock MyLauncher):

| Метод | Путь |
|---|---|
| `GET` | `/api/packs?channel=stable\|beta` |
| `GET` | `/api/packs/{packId}/versions?channel=stable\|beta` |
| `GET` | `/api/packs/{packId}/versions/{version}/manifest?channel=stable\|beta` |
| `GET` | `/api/packs/{packId}/icon` |
| `GET` | `/api/files/sha256:{hex}?packId=&version=&channel=` |

Пример (forge, 1.20.1):

```jsonc
{
  "manifestVersion": 1,
  "packId": "create-expert",
  "version": "1.4.0",
  "channel": "stable",
  "name": "Create Expert",
  "description": "",
  "authors": ["NEXUS"],
  "categories": ["tech"],
  "minecraft": {
    "version": "1.20.1",
    "loader": "forge",
    "loaderVersion": "47.4.10"
  },
  "java": { "major": 17 },
  "files": [
    {
      "path": "mods/create-0.5.1.jar",
      "hash": "sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "size": 1234567,
      "url": "/api/files/sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "required": true
    }
  ],
  "settings": {}
}
```

Снимок создаётся при публикации в колонках `launcher_manifest`,
`launcher_manifest_hash` и `launcher_manifest_schema` и не пересобирается.
Публикация блокируется, если путь/расширение/Java/загрузчик несовместимы с
клиентом. `side = server` в клиентский манифест не попадает; `enabled = false`
не попадает; исчезнувшие файлы просто отсутствуют в новом полном списке.
