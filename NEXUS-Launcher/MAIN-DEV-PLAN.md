# NEXUS-launcher
## Полное техническое задание на разработку Minecraft Launcher

**Название проекта:** NEXUS-launcher  
**Тип продукта:** самостоятельный настольный Minecraft Launcher  
**Основной язык:** Rust  
**Целевая платформа:** Windows 11 (приоритет), архитектура с возможностью последующего портирования  
**Версия документа:** 1.0  
**Статус:** спецификация разработки

---

# 1. Общая концепция проекта

Разработать полноценный Minecraft Launcher под названием **NEXUS-launcher**.

Это самостоятельное приложение для установки, настройки, управления и запуска Minecraft, поддерживающее ванильные версии игры, модифицированные клиенты, модпаки и собственные игровые серверы.

Лаунчер не должен зависеть от MWS-NEXUS или NEXUS Workspace для своей основной функциональности.

NEXUS Workspace является исключительно дополнительным источником игровых сборок. Подключение к нему осуществляется через отдельный модуль интеграции.

## 1.1. Основные принципы

1. Самостоятельная работа без подключения к NEXUS Workspace.
2. Полноценное управление Minecraft разных версий.
3. Изолированные игровые экземпляры (Instances).
4. Поддержка официальной авторизации Microsoft.
5. Поддержка сторонних систем авторизации через расширяемую архитектуру.
6. Установка и управление модификациями.
7. Создание и управление локальными Minecraft-серверами.
8. Безопасная работа с файлами, токенами и игровыми процессами.
9. Современный интерфейс в едином стиле NEXUS.
10. Модульная архитектура, позволяющая расширять возможности без переписывания ядра.

## 1.2. Основные разделы приложения

- Главная — обзор, выбранный инстанс, профиль, быстрый запуск.
- Играть — управление игровыми экземплярами.
- Версии — каталог версий Minecraft и загрузчиков.
- Моды и контент — поиск и управление модификациями.
- Аккаунты — игровые учётные записи.
- Серверы — создание и управление локальными серверами.
- NEXUS Builds — получение сборок из NEXUS Workspace.
- Загрузки — единая очередь всех загрузок.
- Настройки — конфигурация приложения.
- Логи — диагностика, игровые логи и отчёты об ошибках.

# 3. Система игровых инстансов

Это центральная функциональная часть лаунчера.

Каждый инстанс представляет собой независимую установку Minecraft со своими файлами, модами, настройками и конфигурациями.

## 3.1. Возможности

Пользователь может:

- Создать новый инстанс.
- Удалить инстанс.
- Переименовать инстанс.
- Клонировать инстанс.
- Архивировать инстанс.
- Импортировать готовую сборку.
- Экспортировать сборку.
- Изменять иконку.
- Изменять описание.
- Настраивать версию игры.
- Выбирать загрузчик.
- Назначать отдельный Java Runtime.
- Настраивать выделение RAM.
- Устанавливать собственные JVM и игровые аргументы.
- Создавать резервные копии.
- Восстанавливать инстанс.

## 3.2. Изоляция

Каждый инстанс хранится отдельно.

Пример:

```text
NEXUS-launcher-data/
├── instances/
│   ├── vanilla-1/
│   │   ├── instance.json
│   │   ├── game/
│   │   ├── mods/
│   │   ├── config/
│   │   ├── resourcepacks/
│   │   ├── shaderpacks/
│   │   ├── saves/
│   │   └── logs/
│   ├── fabric-survival/
│   └── modded-adventure/
├── assets/
├── libraries/
├── versions/
├── java/
├── downloads/
├── backups/
└── launcher.db
```

Рекомендуется использовать общий кэш библиотек и игровых assets там, где это безопасно, но конфигурации, моды, миры и изменяемые игровые файлы должны принадлежать конкретному инстансу.

Нельзя допускать ситуации, когда обновление модов одного инстанса изменяет содержимое другого.

## 3.3. Instance Manifest

Каждый экземпляр должен иметь собственный манифест.

Пример:

```json
{
  "schema_version": 1,
  "id": "fabric-survival",
  "name": "Fabric Survival",
  "game_version": "1.21.1",
  "loader": {
    "type": "fabric",
    "version": "0.16.9"
  },
  "java": {
    "runtime": "auto",
    "path": null
  },
  "memory": {
    "min_mb": 1024,
    "max_mb": 6144
  },
  "game_directory": "game",
  "created_at": "2026-01-01T00:00:00Z"
}
```

Схема должна версионироваться. Неизвестные будущие поля должны обрабатываться безопасно.

# 4. Управление версиями Minecraft

## 4.1. Поддержка версий

Реализовать получение официального Version Manifest Mojang.

Поддержать:

- Release.
- Snapshot.
- Old Alpha.
- Old Beta.
- Исторические версии.
- Последние доступные версии.

Не хранить список версий в коде. Каталог должен обновляться через официальный источник метаданных и кэшироваться.

Для каждой версии получать:

- ID.
- Тип.
- Дату выпуска.
- URL JSON.
- Main Class.
- Требования Java.
- Libraries.
- Assets.
- Client JAR.
- Logging configuration.
- Аргументы запуска.

## 4.2. Установка

Процесс установки:

1. Получение Version Manifest.
2. Получение JSON конкретной версии.
3. Проверка требований к Java.
4. Подготовка каталогов.
5. Загрузка client JAR.
6. Загрузка библиотек.
7. Загрузка assets.
8. Загрузка natives.
9. Проверка SHA-1/SHA-256 по доступным официальным контрольным суммам.
10. Проверка целостности.
11. Создание локального профиля.
12. Сохранение состояния установки.

Установка должна быть потоковой и не загружать большие файлы целиком в RAM.

При прерывании соединения поддержать продолжение загрузки, если источник поддерживает HTTP Range. Если сервер не поддерживает Range, файл должен безопасно скачиваться заново.

# 5. Поддержка мод-загрузчиков

Реализовать отдельные адаптеры для каждого загрузчика.

## 5.1. Обязательные загрузчики

- Vanilla.
- Fabric.
- Forge.
- NeoForge.
- Quilt.

## 5.2. Дополнительные загрузчики

- OptiFine.
- LiteLoader — только для совместимых исторических версий.

Каждый загрузчик должен иметь собственный installer adapter.

Установка не должна основываться на ручной подмене файлов без проверки совместимости.

## 5.3. Требования

- Получение доступных версий загрузчика.
- Выбор версии.
- Проверка совместимости с Minecraft.
- Загрузка необходимых файлов.
- Установка библиотек.
- Регистрация launch profile.
- Удаление загрузчика из инстанса, если это возможно без повреждения данных.
- Диагностика ошибок установки.

Для каждого адаптера предусмотреть независимые тесты.

# 7. Авторизация и аккаунты

## 7.1. Microsoft

Реализовать официальный процесс авторизации Microsoft с соблюдением требований Microsoft и Mojang.

Не использовать сторонние обходные методы получения игровых токенов.

Процесс должен поддерживать:

- OAuth 2.0 Authorization Code + PKCE либо подходящий официальный Device Code Flow.
- Microsoft account authentication.
- Xbox Live authentication.
- XSTS.
- Minecraft Services authentication.
- Проверку владения Minecraft Java Edition.
- Получение игрового профиля.
- Обновление токенов.
- Завершение сессии.

Точный flow должен соответствовать актуальной официальной документации и требованиям регистрации приложения.

## 7.2. Другие аккаунты

Архитектура должна позволять добавлять провайдеры:

- Ely.by.
- Azuriom.
- Другие совместимые системы авторизации.

Реализовать их как независимые Authentication Providers.

## 7.3. Offline Mode

Поддержать локальные офлайн-профили.

Ограничения:

- Offline-профиль не является подтверждённым Microsoft-аккаунтом.
- Не выдавать его за лицензионную авторизацию.
- Не подменять и не обходить официальную проверку владения игрой.
- Отображать тип аккаунта в интерфейсе.
- Не передавать фиктивные данные авторизации официальным сервисам.
- Не скрывать ограничения совместимости с серверами.

## 7.4. Управление профилями

- Несколько аккаунтов.
- Переключение активного профиля.
- Отображение игрового ника и аватара.
- Статус авторизации.
- Повторная авторизация.
- Удаление аккаунта из лаунчера.
- Безопасное обновление токенов.

## 7.5. Хранение токенов

Не хранить секреты в открытом JSON или SQLite.

На Windows использовать Windows Credential Manager или DPAPI.

Не записывать токены, коды авторизации, пароли и чувствительные данные в логи.

# 10. Интеграция NEXUS Workspace

## 10.1. Основной принцип

Интеграция является дополнительной функцией.

NEXUS-launcher должен работать без NEXUS Workspace.

В приложении создать отдельный раздел:

**NEXUS Builds**

Назначение — получение опубликованных сборок с сервера NEXUS Workspace и установка их в виде самостоятельных игровых инстансов.

Не связывать основную авторизацию лаунчера с авторизацией NEXUS Workspace.

Не требовать наличия аккаунта NEXUS для использования обычных функций лаунчера.

## 10.2. Совместимость с существующей системой

Ориентироваться на NEXUS Workspace 1.0.0 и его существующий Launcher API.

Согласно README.md системы:

- Базовый API-префикс: `/api/v1`.
- Внутренний Launcher API использует Bearer-токены.
- Поддерживаемые scopes: `launcher.catalog` и `launcher.artifacts`.
- Публичный каталог MyLauncher доступен через `/api/packs/`.
- Файлы публичного репозитория доступны через `/api/files/`.
- Публичный MyLauncher не требует токена.
- Приватные сборки недоступны обычному stock-клиенту.
- Для внутренних операций предусмотрен механизм токенов лаунчера.
- Манифест сборки использует `schema_version: "1.0"`.
- Файлы описываются относительными путями, SHA-256, размерами и ссылками на скачивание.
- Локальные физические пути сервера не раскрываются.

### Критически важное требование

Перед реализацией интеграции обязательно изучить:

`docs/LAUNCHER_CONTRACT.md`

Также проверить:

- `docs/API.md`
- `docs/MANIFEST.md`
- `docs/openapi.json`
- `docs/SECURITY.md`

Фактический контракт сервера является источником истины.

Не придумывать URL, JSON-поля, HTTP-методы, заголовки, параметры авторизации или формат ответов, если их нет в документации.

## 10.3. Настройка подключения

Пользователь может:

- Добавить сервер.
- Указать URL.
- Проверить соединение.
- Удалить сервер.
- Включить или отключить источник.
- Просматривать состояние соединения.
- Обновить каталог сборок.

Не зашивать адрес одного сервера в приложение.

Предусмотреть несколько источников NEXUS Workspace.

Проверять HTTPS, валидность URL и сертификат. Не отключать проверку TLS.

## 10.4. Получение сборок

В разделе NEXUS Builds отображать:

- Название.
- Иконку.
- Описание.
- Версию Minecraft.
- Загрузчик.
- Версию сборки.
- Дату релиза.
- Размер загрузки.
- Статус доступности.
- Changelog.
- Информацию о серверной и клиентской стороне.

Данные брать только из фактического API и манифеста.

Не использовать демонстрационные сборки.

## 10.5. Установка сборки

Алгоритм:

1. Получить каталог.
2. Выбрать сборку.
3. Получить опубликованный релиз.
4. Получить manifest.
5. Проверить `schema_version`.
6. Проверить обязательные поля.
7. Проверить относительные пути.
8. Проверить размеры файлов.
9. Проверить SHA-256.
10. Скачать необходимые артефакты.
11. Проверить целостность каждого файла.
12. Определить Minecraft и загрузчик.
13. Подготовить зависимости.
14. Установить клиентские файлы.
15. Создать отдельный инстанс.
16. Сохранить источник и идентификатор установленного релиза.
17. Отобразить результат.

Публикация нового релиза не должна автоматически изменять уже установленную сборку.

Обновление выполняется только по инициативе пользователя либо согласно явно включённой настройке.

## 10.6. Разделение client/server

Учитывать категории и стороны файлов:

- `mods`
- `config`
- `resourcepacks`
- `shaderpacks`
- `scripts`
- `overrides`
- `other`

Поддерживать стороны:

- `client`
- `server`
- `both`

При установке клиентской сборки:

- устанавливать `client`;
- устанавливать `both`;
- не устанавливать исключительно серверные файлы.

При подготовке серверной сборки:

- устанавливать `server`;
- устанавливать `both`;
- исключать исключительно клиентские файлы.

Сохранять исходную структуру относительных путей и правила манифеста.

## 10.7. Приватные сборки

Не пытаться обходить ограничения публичного API.

Для доступа к приватным сборкам использовать только документированный внутренний Launcher API и выданные для этого права.

Не использовать браузерную cookie-сессию администратора NEXUS Workspace как способ авторизации лаунчера.

Не хранить Bearer-токен в открытом конфигурационном файле.

Пользователь должен явно добавлять или получать разрешённый способ подключения к приватному источнику.

Токен должен храниться в системном защищённом хранилище.

## 10.8. Отказоустойчивость

Если сервер недоступен:

- локальные инстансы продолжают работать;
- локальные моды доступны;
- Minecraft запускается без обращения к серверу;
- показывается ошибка подключения;
- ранее загруженные данные не удаляются;
- незавершённые загрузки можно продолжить;
- каталог можно обновить повторно.

# 17. Безопасность

Безопасность обязательна на уровне архитектуры, а не как дополнительная функция.

## 17.1. Файловая система

Защититься от:

- Path Traversal.
- Абсолютных путей в архивах.
- Символических ссылок.
- Junctions.
- Zip Slip.
- Перезаписи файлов вне инстанса.
- Подмены загруженных файлов.
- Некорректных имён.
- Чрезмерного размера архивов.
- Zip Bomb.

Перед записью проверять канонический путь и принадлежность целевому каталогу.

Учитывать особенности Windows и файловые операции с junction/reparse points.

## 17.2. Tauri Security

- Минимальные Tauri capabilities.
- Минимальные разрешения.
- Не предоставлять frontend произвольный доступ к shell.
- Не разрешать выполнение произвольных системных команд.
- Валидировать все входные данные команд.
- Использовать строго типизированные аргументы.
- Не доверять данным frontend.
- Ограничить навигацию приложения.
- Запретить произвольные remote origins для локального интерфейса.

## 17.3. Процессы

Minecraft и серверы запускать через безопасное создание процессов.

Не формировать shell-команды из пользовательского ввода.

Передавать аргументы отдельными элементами массива.

Ограничивать процессы только соответствующими каталогами и рабочими директориями.

## 17.4. Сетевая безопасность

- TLS verification.
- Защита от SSRF.
- Проверка URL внешних источников.
- Запрет опасных локальных адресов для внешних источников.
- Контроль редиректов.
- Ограничение размера ответа.
- Таймауты.
- Ограничение параллельных запросов.

Для пользовательских серверов NEXUS предусмотреть отдельную политику доверия. Локальные и частные адреса могут быть необходимы в self-hosted окружении, поэтому их нельзя безусловно блокировать без возможности осознанной настройки.

## 17.5. Логи

Не записывать:

- Access tokens.
- Refresh tokens.
- Пароли.
- Коды авторизации.
- Секреты.
- Полные чувствительные заголовки HTTP.

# 23. Критерии окончательной приёмки

Проект считается готовым, когда:

1. Приложение запускается без установленного NEXUS Workspace.
2. Можно создавать независимые инстансы.
3. Можно устанавливать и запускать Minecraft.
4. Поддерживаются основные загрузчики.
5. Работает Java Manager.
6. Работает официальная Microsoft-авторизация.
7. Поддерживаются локальные офлайн-профили.
8. Работает установка модов.
9. Работает импорт и экспорт модпаков.
10. Работает отдельный раздел NEXUS Builds.
11. Реально устанавливаются опубликованные сервером сборки.
12. Проверяются manifest и SHA-256.
13. Client/server файлы устанавливаются корректно.
14. Приватные сборки не доступны без соответствующих прав.
15. Можно создавать локальные Minecraft-серверы.
16. Работают консоль и управление сервером.
17. Работают резервные копии.
18. Нет критических ошибок безопасности.
19. Интерфейс соответствует стилю NEXUS.
20. Фоновая анимация работает непрерывно.
21. Все основные сценарии покрыты тестами.
22. Приложение имеет документацию и установщик.

# 24. Правила разработки для AI-разработчика

Следовать этим правилам на протяжении всего проекта:

1. Не создавать декоративные кнопки без функционала.
2. Не использовать фиктивные данные вместо реальных интеграций.
3. Не подменять реальные загрузки искусственным прогрессом.
4. Не оставлять TODO в критических функциях.
5. Не отключать проверки безопасности ради упрощения реализации.
6. Не объединять независимые модули в один большой файл.
7. Не менять существующий API NEXUS Workspace ради удобства лаунчера.
8. Не привязывать основной функционал к NEXUS Workspace.
9. Не удалять игровые данные при обновлении приложения.
10. Не хранить токены в открытом виде.
11. Не запускать пользовательский ввод через shell.
12. Не считать HTTP-ответ успешным без проверки содержимого и целостности.
13. Не переходить к следующему этапу при проваленных критических тестах.
14. Документировать все реализованные функции.
15. После каждого этапа предоставлять отчёт: что сделано, что протестировано, какие ограничения остались.

Если внешний сервис недоступен, показывать реальную ошибку и сохранять возможность работы с локальными данными.

Если API не соответствует ожидаемому контракту, не пытаться угадывать структуру ответа.

**Главный приоритет: реальная работоспособность, безопасность, независимость и расширяемость NEXUS-launcher.**

Конечный продукт должен быть полноценным Minecraft Launcher, а не интерфейсной демонстрацией или оболочкой для NEXUS Workspace.
