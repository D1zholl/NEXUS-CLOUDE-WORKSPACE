# Архитектурные решения NEXUS-launcher (ADR)

**Версия документа:** 1.0
**Дата:** 21.11.2026
**Статус:** проект. Реализация не начата.
**Связанные документы:** `docs/ARCHITECTURE.md`, `docs/DATABASE.md`,
`docs/COMMANDS.md`, `docs/EVENTS.md`.

Каждое решение фиксирует контекст, выбор, следствия и отклонённые
альтернативы. Решение можно пересмотреть только новым ADR, а не правкой
старого.

## ADR-001. Cargo workspace из 8 крейтов + `src-tauri`

**Контекст.** ТЗ предлагает один `src-tauri/src` с 20 модулями. Референсный
клиент дошёл до файлов 85–123 КБ, которые трудно тестировать. Ранний черновик
roadmap перечислял 15 крейтов; для текущего объёма это преждевременное
дробление.

**Решение.** Восемь библиотечных крейтов:

```
nexus-core, nexus-platform, nexus-auth, nexus-game,
nexus-instances, nexus-content, nexus-ops, nexus-nexus
```

плюс тонкий `src-tauri` и `frontend`. Каждый крейт имеет минимум два модуля,
свой тип ошибок и тесты. Домен не зависит от Tauri. `src-tauri` — только
композиция, DTO и события.

**Следствия.**

- Направление зависимостей проверяется CI (`cargo metadata`, `cargo deny`).
- `nexus-game` не знает про инстансы; передаются `InstallTarget` и
  `LaunchRequest`.
- `nexus-content` и `nexus-nexus` не пишут файлы напрямую.
- Появится позже необходимость в отдельном крейте — это новый ADR, а не
  «на всякий случай».

**Отклонено.** 15 крейтов (циклы и накладные расходы); один crate (монолит);
`src-tauri` как единственный доменный слой (нельзя тестировать без Tauri).

## ADR-002. Baseline зависимостей и версий

**Контекст.** Аудит зафиксировал: SQLx и `rusqlite` несовместимы
(`links = "sqlite3"`); Tauri 2.12 тянет `reqwest 0.13`; TypeScript 7
несовместим с `typescript-eslint`; мажорные апгрейды `sqlx 0.9`, `zip 9`,
`keyring 4` требуют проверки API.

**Решение.**

- Rust stable, Edition 2024; MSRV набора ≤ 1.95.
- `reqwest 0.13` (rustls, stream, system-proxy) — один HTTP-стек.
- `sqlx 0.9` (`runtime-tokio`, `sqlite-bundled`, `migrate`, `chrono`, `uuid`);
  **без `rusqlite`** даже в тестах.
- `zip 9` с `default-features = false, features = ["deflate"]`.
- `windows 0.62`, `sysinfo 0.40` — совпадают с Tauri, меньше дублей.
- `keyring` — версия 3.6 как проверенная; 4.x только после спайка.
- Frontend: React 19.3.x, TypeScript **6.0.3**, Vite 8.3.x, Vitest 5.1.x,
  `@tauri-apps/api` 2.12.x.
- Один `Cargo.lock` и один `package-lock.json` в git.

**Следствия.**

- Спайки до этапов 3/7: API `sqlx 0.9`, `zip 9`, `keyring`, Forge installer.
- Обновление мажоров — отдельный PR + ADR + прогон security-тестов.
- Tauri crate/CLI/JS API обновляются одной линией.

**Отклонено.** «Всё latest» без спайков; `reqwest 0.12`; `rusqlite`; TS 7.

## ADR-003. Данные в `%LOCALAPPDATA%`, per-user, без portable

**Контекст.** Инстансы, assets и Java занимают десятки гигабайт. Roaming
непригоден. Portable-режим усложняет пути, обновления и безопасность. UAC и
per-machine установка не нужны лаунчеру.

**Решение.**

- Корень данных: `%LOCALAPPDATA%\NEXUS-Launcher`, фиксирован.
- Установка per-user; данные не требуют прав администратора.
- Dev-переопределение: `NEXUS_LAUNCHER_DATA_DIR` (только dev/тесты).
- `config.toml` лежит внутри корня и **не может** переместить корень.
- Portable-режим в v1 отсутствует.

**Следствия.**

- Данные не синхронизируются между профилями Windows — это ожидаемо.
- Обновление/удаление лаунчера не трогает корень данных.
- Резервная копия данных — ответственность пользователя + Backup Manager.

**Отклонено.** Roaming; `%PROGRAMDATA%`; portable-режим в v1; перемещение
корня из `config.toml` (курица и яйцо).

## ADR-004. View-state роутинг и один Canvas-фон

**Контекст.** ТЗ требует непрерывный анимированный фон и 10 разделов.
React Router 8 — мажорный переход с неясным поведением; Three.js добавляет
вес и WebGL-риски.

**Решение.**

- Роутинг — собственный view-state (типизированный `Screen` union) на MVP.
- Фон — один Canvas-слой на уровне layout, не перезапускается при навигации.
- Пауза при `visibilitychange`, лимит FPS, `prefers-reduced-motion`,
  CSS fallback.
- Three.js не входит в MVP; может быть добавлен позже за фича-флагом.
- Переходы — CSS-анимации; без тяжёлых библиотек.

**Следствия.**

- Нет deep-linking и browser history; для desktop это не требуется.
- При появлении сложных вложенных маршрутов решение пересматривается.
- Фон не влияет на FPS игры: пауза при скрытом окне и лимит кадров.

**Отклонено.** React Router 8 сразу; отдельный Canvas на каждой странице;
Three.js в MVP.

## ADR-005. SQLite как индекс, WAL, forward-only миграции, без шифрования

**Контекст.** Нужны локальные данные, миграции между версиями, устойчивость к
сбоям. Пользовательские файлы (миры, моды) не должны зависеть от БД.
Шифрование БД требует отдельного крейта/сборки SQLite.

**Решение.**

- SQLite + WAL + `foreign_keys=ON` + `busy_timeout=5000`.
- SQLx `migrate!`, только вперёд; изменение применённой миграции запрещено.
- БД — индекс; `instance.json`/`server.json` — источник истины.
- БД можно пересоздать сканированием манифестов.
- Шифрование БД не применяется: секретов в ней нет.
- Бэкап перед миграцией — `VACUUM INTO`; более новая схема → отказ старта.

**Следствия.**

- Нет down-миграций; откат — из бэкапа.
- `running` job-ы при рестарте становятся `interrupted`.
- Повреждение БД не означает потерю инстансов.

**Отклонено.** ORM; шифрование SQLite; мягкое удаление всех таблиц;
двухфазные миграции с down.

## ADR-006. Каталог инстанса по UUID, `game/` — игровая директория, manifest + lock

**Контекст.** ТЗ одновременно показывает `mods/` на уровне инстанса и
`game_directory: "game"`, что несовместимо с тем, как Minecraft ищет моды.
Переименование инстанса не должно ломать пути. Пользовательские и управляемые
файлы нужно различать.

**Решение.**

- Каталог: `instances/<uuid>/`; имя — только в манифесте.
- `game/` — `cwd` и `gameDirectory` Minecraft; моды, конфиги, миры внутри.
- `instance.json` — пользовательская конфигурация.
- `instance.lock.json` — управляемый инвентарь файлов и профиль запуска.
- Общие assets/libraries/versions — вне инстанса.
- Смена MC/loader — переустановка (`instances_change_version`), не «тихое»
  изменение.

**Следствия.**

- Клонирование копирует `game/` и создаёт новый lock.
- Пользовательские файлы (`managed=0`) не удаляются при обновлении сборки.
- `game_directory` в v1 фиксирован как `"game"`.

**Отклонено.** Каталог по имени; `mods/` вне `game/`; единый файл
manifest+lock; хранение абсолютных путей в манифесте.

## ADR-007. Отдельный Server Manifest, `server/`, EULA-gate

**Контекст.** Сервер — самостоятельный экземпляр, не связанный с клиентским
инстансом. EULA нельзя принимать автоматически. Сервер должен переживать
закрытие лаунчера.

**Решение.**

- `servers/<uuid>/server.json` + `server.lock.json`.
- Игровая директория — `server/` (world, mods/plugins, свойства).
- `eula=true` пишется только после `servers_accept_eula(accepted=true)`.
- `eula_accepted_at` — журнал, источник истины — `eula.txt`.
- Идентичность процесса — `.nexus/run.json`.
- Auto-restart только для `crashed`, с лимитом и backoff.

**Следствия.**

- Сервер не зависит от инстанса и его модов.
- Восстановление после рестарта лаунчера — по `RunIdentity`, не по PID.
- Серверные и клиентские сборки NEXUS разделены.

**Отклонено.** Общий каталог с клиентом; автопринятие EULA; хранение PID как
достаточного признака.

## ADR-008. Двухуровневая конфигурация

**Контекст.** Часть настроек нужна до открытия БД (пути, логи, сеть), часть —
меняется из UI и должна версионироваться/мигрироваться. Секреты нельзя
хранить ни там, ни там.

**Решение.**

- `config.toml` — bootstrap: сеть, загрузки, логирование, security-флаги.
- `app_settings` — пользовательские настройки UI и значения по умолчанию.
- Секреты — keyring, только `secret_ref` в БД.
- Приоритет: defaults → `config.toml` → `app_settings`.
- `config.toml` читается/пишется атомарно; неизвестные ключи сохраняются.

**Следствия.**

- Дублирования настроек нет: каждая живёт в одном месте.
- Изменения bootstrap-настроек требуют перезапуска и помечаются
  `requiresRestart`.
- UI не редактирует `config.toml` напрямую; только типизированные группы.

**Отклонено.** Всё в БД (нельзя открыть БД без конфига); всё в TOML (нет
миграций и UI-настроек); секреты в конфиге.

## ADR-009. Типизированный IPC, job-модель, единый error envelope

**Контекст.** UI не должен управлять ФС и процессами. Долгие операции нельзя
держать в синхронном вызове. Ошибки должны быть понятны пользователю и
пригодны для автоматической обработки.

**Решение.**

- Только `#[tauri::command]` с DTO; `invoke` — в одном слое frontend.
- Операции > 10 с — job: `{ jobId }` + события `job:*`.
- Один `ErrorDto` с `code`, `message`, `details`, `retryable`, `requestId`.
- Валидация формы — на границе, смысла — в домене.
- Неидемпотентные команды не повторяются автоматически.
- Отмена — кооперативная, через `CancellationToken`.

**Следствия.**

- UI всегда может показать прогресс и отмену.
- Ошибки не содержат SQL/HTTP/путей.
- Новые команды добавляются аддитивно; удаление — новая версия IPC.

**Отклонено.** Один универсальный `execute(action, payload)`; «сырые» ошибки;
синхронные многоминутные команды; автоматические retry на уровне UI.

## ADR-010. События — уведомления, не транспорт состояния

**Контекст.** Прогресс, консоль и метрики нужны в реальном времени, но
события могут теряться при скрытом/перезагруженном WebView. Если UI строит
состояние только из событий, он рассинхронизируется.

**Решение.**

- Конверт события: `schemaVersion`, `eventId`, `occurredAt`, `jobId`,
  `entity`, `seq`, `payload`.
- Событие — уведомление; авторитетное состояние — команда.
- Троттлинг 10 Гц, батчинг консоли, коалесинг прогресса.
- Один подписчик на frontend, инвалидация query-ключей.
- `seq` для потоков, дедупликация в UI.
- Запрет секретов и абсолютных путей в payload.

**Следствия.**

- После `visibilitychange` UI делает добор состояния.
- Потеря события не ломает приложение.
- Консоль ограничена ring buffer-ом; полный лог — на диске.

**Отклонено.** События как единственный источник; поток каждого байта
прогресса; неограниченные очереди; передача токенов в payload.

## ADR-011. Frontend без произвольной ФС и shell

**Контекст.** XSS в WebView не должен превращаться в доступ к файлам и
процессам. ТЗ прямо запрещает frontend управлять ФС и запускать команды.

**Решение.**

- Нет Tauri `fs`, `shell`, `http`, `process` plugins.
- `plugin-dialog` — только open/save; путь — недоверенный ввод.
- `plugin-opener` — только `https` из allowlist.
- `assetProtocol` — только иконки инстансов/серверов.
- Строгий CSP; capabilities только для main-window.
- Любая файловая операция — команда с `RootedDir`/`SafeRelPath`.

**Следствия.**

- UI не может показать произвольный файл; только предусмотренные операции.
- Импорт архива возможен, но только через Rust и с лимитами.
- Навигация на внешние origin внутри WebView запрещена.

**Отклонено.** `fs` plugin с широким scope; shell для «удобства»; загрузка
удалённого контента в WebView; отключение TLS.

## ADR-012. Модель процессов

**Контекст.** Нужно запускать игру, серверы и сторонние installer-ы.
`KILL_ON_JOB_CLOSE` защищает от зомби, но убивает игру/сервер при закрытии
лаунчера, что противоречит ожиданиям пользователя и требованию восстановления
сервера. Восстановить stdin после рестарта без отдельного процесса нельзя.

**Решение.**

- Два режима Job Object:
  - `Ephemeral` (installer, probe) — `KILL_ON_JOB_CLOSE`, stdout/stderr через
    pipe;
  - `Persistent` (игра, сервер) — без kill-on-close, дерево убивается только
    явной командой, stdout/stderr сразу в файл, stdin через pipe.
- Файловое перенаправление вывода обязательно: pipe после выхода лаунчера
  закрылся бы, и сервер получил бы ошибку записи. Файл также служит источником
  консоли при восстановлении.
- Stdin остаётся pipe; после выхода лаунчера сервер получает EOF и должен
  продолжить работу (проверяется тестом). Иначе нужен sidecar, а не остановка
  сервера.
- Идентичность процесса: PID + время создания + путь exe + хэш командной
  строки (если доступен) + `launch_nonce`.
- При старте лаунчера серверы восстанавливаются по `run.json`; при
  несовпадении — `Lost`, процесс не убивается.
- MVP: attached supervisor; после рестарта лаунчера доступен tail лога, но
  stdin не восстанавливается (консоль read-only).
- Sidecar-supervisor с named pipe — отдельное решение после MVP.

**Следствия.**

- Закрытие лаунчера не останавливает игру/сервер; логи продолжают писаться.
- Возможны «осиротевшие» процессы, но они отслеживаются и не маскируются.
- Полноценная отправка команд после рестарта отложена; это явно показано в UI.

**Отклонено.** Всегда `KILL_ON_JOB_CLOSE`; всегда убивать при выходе; PID как
достаточный идентификатор; sidecar сразу (сложность и ещё один бинарник).

## ADR-013. Адаптеры загрузчиков и изоляция installer-ов

**Контекст.** Fabric/Quilt имеют простой meta-формат; Forge/NeoForge
используют сторонние installer-jar. NeoForge Maven недоступен с целевой
машины. Точные CLI-ключи Forge installer не проверены.

**Решение.**

- `LoaderAdapter` на каждый загрузчик; Vanilla — no-op.
- Fabric/Quilt — meta + profile merge, без исполнения стороннего кода.
- Forge — официальный installer в изолированном staging, проверка
  опубликованного SHA-1/размера, ограниченный `java.io.tmpdir`.
- NeoForge — адаптер есть, но возвращает `LOADER_UNAVAILABLE`, пока сеть не
  доступна; не маскируется под успех.
- Точные ключи installer-ов фиксируются в спайке до реализации, а не
  выдумываются.
- OptiFine/LiteLoader — вне v1.

**Следствия.**

- Установка Forge может быть недоступна в офлайн-окружении.
- NeoForge не блокирует остальные этапы.
- Сторонний installer не получает доступ к произвольным каталогам.

**Отклонено.** Ручная подмена файлов без installer-а; встраивание installer-ов
в ресурсы; «примерные» CLI-ключи без проверки.

## ADR-014. CurseForge отложен

**Контекст.** Официальный API требует ключ; встраивать его в desktop-клиент
нельзя (извлекается из бинарника). Terms ограничивают распространение.
Импорт CF-модпака без ключа невозможен.

**Решение.**

- v1 не поддерживает CurseForge и импорт CF-модпаков.
- `provider='curseforge'` зарезервирован в схемах, но не реализован.
- Варианты на будущее: пользовательский ключ, собственный proxy, официальное
  партнёрство. Решение — отдельный ADR после юридической проверки.

**Следствия.**

- UI не показывает неработающий источник.
- Модпаки CF отклоняются с `MODPACK_UNSUPPORTED`.
- Нет риска утечки ключа.

**Отклонено.** Встроенный ключ; скрейпинг сайта; обход Cloudflare.

## ADR-015. NEXUS Workspace — runtime-optional, public-only в v1

**Контекст.** Лаунчер обязан работать без NEXUS. Публичный контракт проверен:
каталог, версии, манифест, файлы, SHA-256, Range. Приватные сборки требуют
Bearer-токен, которого в публичном клиенте нет. Публичный манифест уже
отфильтрован по `side=client|both`.

**Решение.**

- Крейт `nexus-nexus` компилируется всегда, но сетевых вызовов без источника
  нет.
- Источник по умолчанию отсутствует; пользователь добавляет URL.
- v1 — только публичный API без токена.
- Приватный режим возвращает `NEXUS_PRIVATE_UNAVAILABLE`; токен, если
  появится, — только keyring.
- Обновление сборки — только по кнопке; автоматическое запрещено.
- Публикация Quilt в NEXUS не поддерживается контрактом.

**Следствия.**

- Нет обязательной зависимости от сервера.
- Офлайн-инстансы работают.
- Серверные сборки NEXUS вне v1.

**Отклонено.** Cargo feature (усложняет CI без выгоды); обязательный источник;
токен в `config.toml`; автообновление сборок.

## ADR-016. Modrinth — обязательный источник контента v1

**Контекст.** Modrinth API доступен без ключа, поддерживает поиск, версии,
зависимости и `.mrpack`. Требуется корректный User-Agent и учёт rate limit.

**Решение.**

- `ContentProvider` trait; в v1 — только `ModrinthProvider`.
- User-Agent с версией и контактом.
- Кэш метаданных, ETag, backoff на 429.
- Установка только после плана и проверки совместимости.
- CurseForge — см. ADR-014.

**Следствия.**

- Один источник проще тестировать и поддерживать.
- Расширение до второго провайдера не меняет домен.

**Отклонено.** Два источника сразу; скрейпинг; установка без resolver-а.

## ADR-017. Автообновление лаунчера отложено

**Контекст.** Tauri updater требует подписанные артефакты, HTTPS-хостинг и
ключи. Ни того, ни другого, ни сертификата подписи кода сейчас нет.

**Решение.**

- В v1 нет updater-а и декоративных кнопок «проверить обновление».
- Обновление лаунчера — ручная установка новой версии поверх.
- Updater добавляется после появления ключей, подписи и хостинга, отдельным
  ADR.
- Обновление не должно удалять инстансы, Java, аккаунты и бэкапы.

**Следствия.**

- Нет риска недоверенного обновления.
- Пользователь обновляется вручную; это честно отражено в UI.

**Отклонено.** Updater без подписи; обновление с непроверенного источника;
автообновление «для галочки».

## ADR-018. Версионирование манифестов и неизвестных полей

**Контекст.** Контракты внешних источников и собственные форматы будут
эволюционировать. Старый лаунчер не должен портить новые данные.

**Решение.**

- `schema_version` у `instance.json`, `server.json`, lock-файлов, БД, событий
  и IPC.
- Неизвестные поля сохраняются (`#[serde(flatten)] extra`).
- Более новая версия манифеста → read-only + явная ошибка, без «умной»
  интерпретации.
- Аддитивные поля не меняют версию; несовместимые — новая версия + миграция.
- Перед миграцией — `.bak`.

**Следствия.**

- Откат лаунчера не теряет пользовательские данные.
- Валидация строгая к обязательным полям и терпимая к будущим.

**Отклонено.** Игнорирование `schema_version`; перезапись манифеста без
сохранения неизвестных полей; «автоматическая догадка» о новых полях.

## ADR-019. Один HTTP-стек через `nexus-platform::net`

**Контекст.** Tauri уже тянет `reqwest 0.13`. Доменные крейты могли бы
добавить свой `reqwest`, но тогда политики TLS/redirect/таймаутов
разъедутся.

**Решение.**

- Все запросы — через `HttpClient` в `nexus-platform::net`.
- Доменные крейты не зависят от `reqwest`.
- Один набор политик: TLS, redirects, таймауты, User-Agent, retry, лимит
  ответа, proxy.
- Исключения (redirect policy) задаются `RequestProfile`, а не новым
  клиентом.

**Следствия.**

- Нельзя незаметно отключить TLS в одном модуле.
- Тестирование сети централизовано (mock-сервер).
- Новый источник = новый профиль, а не новый стек.

**Отклонено.** `reqwest` в каждом крейте; HTTP из WebView; отключение
проверки TLS.

## ADR-020. Формат бэкапа и restore через staging

**Контекст.** Бэкап должен быть переносимым, проверяемым и безопасным.
Восстановление не должно уничтожать данные при ошибке.

**Решение.**

- Zip-архив + `backup.json` (schema, target, entries с SHA-256).
- Запись в staging, затем атомарное переименование.
- Restore: проверка архива → staging → pre-restore snapshot → замена.
- Для работающего сервера — `save-off`/`save-all`/`save-on`.
- Retention не удаляет последний валидный бэкап.
- Запущенный клиент не бэкапится в v1.

**Следствия.**

- Двойное место на диске на время restore; проверяется preflight.
- Архив можно проверить без распаковки.
- Повреждённый архив не приводит к удалению текущих данных.

**Отклонено.** Копирование каталога «как есть» без манифеста; restore поверх
без snapshot; бэкап работающего сервера без `save-all`.

## ADR-021. Диагностика только по действию, с redaction

**Контекст.** Диагностический пакет помогает поддержке, но может содержать
пути, логи и случайные секреты. Автоматическая отправка недопустима.

**Решение.**

- Экспорт запускается только пользователем.
- Пакет: логи, crash reports, app info, redacted config, метаданные БД.
- **Не включаются**: SQLite, токены, keyring, полные HTTP-тела.
- Пути сокращаются; полный путь — только по отдельному согласию.
- Redaction по ключам и известным значениям; тест обязателен.

**Следствия.**

- Пакет безопаснее отдавать в поддержку.
- Часть диагностики может быть неполной — это осознанный компромисс.

**Отклонено.** Автоотправка; включение БД; «сырые» логи без фильтра.

## ADR-022. Тестовая политика

**Контекст.** Аудит требует детерминизма, офлайн-unit-тестов и отдельных
security-кейсов. Сеть в CI нестабильна.

**Решение.**

- Unit-тесты не ходят в сеть и не используют `%APPDATA%` разработчика.
- Время/случайность инжектируются (`Clock`, фиксированные UUID в фикстурах).
- Внешние JSON — фикстуры с датой и источником.
- HTTP — mock-сервер; live-тесты под feature-флагом.
- Каждый security-кейс — отдельный тест.
- Upgrade-тесты БД и манифестов — на фикстурах.
- Гейты: fmt, clippy `-D warnings`, test, typecheck, lint, build.

**Следствия.**

- CI воспроизводим.
- Медленные live-проверки — перед релизом, не на каждый PR.
- Coverage — не самоцель; критичные ветви покрываются обязательно.

**Отклонено.** Сеть в unit-тестах; `sleep` для синхронизации; ручная проверка
security-кейсов; тесты, зависящие от машины разработчика.

## ADR-023. Модель аккаунтов без `auth_providers`

**Контекст.** В v1 есть offline и Microsoft. Ely.by/Azuriom — будущие.
Отдельная таблица провайдеров без пользовательских настроек не нужна.

**Решение.**

- Провайдеры — код (`ProviderKind`).
- `accounts.provider` — текстовый enum; уникальность
  `(provider, provider_account_id)`.
- Секрет — `secret_ref` в keyring; offline — `NULL`.
- Таблица `auth_providers` появится только при настройке внешних провайдеров.

**Следствия.**

- Меньше миграций и пустых таблиц.
- Добавление Ely.by/Azuriom не ломает схему.

**Отклонено.** Таблица «на будущее»; хранение токенов в `accounts`.

## ADR-024. Java: точное совпадение major

**Контекст.** Mojang отдаёт `javaVersion.majorVersion`; для 26.2 это Java 25.
Загрузчик может повысить требование. Запуск на «похожей» версии приводит к
непонятным падениям.

**Решение.**

- Требование берётся из метаданных, не из таблицы «версия → Java».
- Приоритет: точный major + arch, затем managed-runtime.
- Нет автоматической подстановки другого major.
- Пользовательский `custom_path` не обходит предупреждение.
- Несовместимость → `JAVA_MISSING`/`JAVA_INCOMPATIBLE` с предложением
  установки.

**Следствия.**

- Больше загрузок Java, но предсказуемый запуск.
- Пользователь видит причину, а не «игра упала».

**Отклонено.** Эвристическая таблица; тихий fallback на Java 8/17; запуск без
проверки.

## ADR-025. Логирование

**Контекст.** Нужны логи лаунчера, игры и серверов, ротация, поиск и
отсутствие секретов. GUI не имеет консоли.

**Решение.**

- `tracing` + `tracing-subscriber`; файлы с ежедневной ротацией и лимитом.
- Отдельные raw-логи игры/сервера (stdout/stderr) с `seq` и временем.
- Span-поля: `jobId`, `instanceId`, `serverId`, `runId`.
- Redaction layer по ключам и значениям.
- Ошибка инициализации логов не убивает приложение.
- Логи не публикуют собственных событий (защита от циклов).

**Следствия.**

- Диагностика читает файлы, а не БД.
- Ротация ограничивает диск.
- Кодировка — UTF-8 с lossy-декодированием.

**Отклонено.** Логи только в БД; запись каждого события в лог; хранение
токенов; отсутствие ротации.

## ADR-026. Декларативный installer, общий кэш, блокировки

**Контекст.** Установка Minecraft — тысячи файлов. Повторная установка должна
быть дешёвой, параллельная — безопасной, сбой — восстановимым.

**Решение.**

- `InstallPlan` — декларативный список файлов; `execute` идемпотентен.
- Проверка существующих файлов по размеру/хэшу; скачивание только
  недостающего.
- Общий кэш `shared/`; версии изолированы по `version_id`.
- Файловая блокировка на установку версии.
- Staging + атомарный rename.
- План не содержит абсолютных путей.

**Следствия.**

- Повторная установка быстрая.
- Параллельные попытки не портят кэш.
- Repair использует тот же план.

**Отклонено.** «Скачать всё заново»; общий каталог без версий; установка без
блокировки; запись напрямую в целевой файл.

## ADR-027. Стабильные коды ошибок

**Контекст.** UI должен реагировать на ошибки программно, поддержка — искать
по коду. Тексты меняются, коды — нет.

**Решение.**

- `ErrorCode` — `SCREAMING_SNAKE_CASE`, стабильный, документированный.
- `message` — пользовательский текст; `details` — безопасные данные.
- Запрещены SQL, HTTP-тела, абсолютные пути, стектрейсы.
- `retryable` — подсказка, не автоматический retry.
- Доменные ошибки конвертируются один раз, в адаптере.
- `requestId` связывает ответ с логом.

**Следствия.**

- UI может показать «Повторить»/«Установить Java» по коду.
- Изменение кода — ломающее изменение.

**Отклонено.** Только человекочитаемые строки; коды-«мусор» вроде `ERROR_1`;
возврат `anyhow`.

## ADR-028. Runtime-настройки вместо Cargo features

**Контекст.** Соблазн закрыть NEXUS/серверы/моды Cargo features. Это
умножает комбинации сборки и CI, а пользователю функции всё равно нужны в
одном бинарнике.

**Решение.**

- Cargo features — только для `dev`/`test`/live-тестов.
- Функции включаются настройками/наличием источника.
- NEXUS без источника не делает сетевых вызовов.
- Отключённая функция не показывается в UI как рабочая.

**Следствия.**

- Один бинарник, один набор тестов.
- Размер бинарника больше, чем при жёстком вырезании; это приемлемо.

**Отклонено.** Feature-флаги на каждый домен; отдельные сборки «lite».

## ADR-029. Атомарные файловые операции и политика Windows-путей

**Контекст.** Windows: длинные пути, junction/reparse points, reserved names,
ADS, регистронезависимость, антивирус. Ошибка в пути = запись вне инстанса.

**Решение.**

- Единый `SafeRelPath`/`RootedDir`; канонизация и проверка вхождения.
- Запрет `..`, абсолютных путей, UNC, ADS, reserved names, хвостовых
  пробелов/точек.
- NFC + case-insensitive уникальность.
- Отказ от symlink/junction-компонентов.
- Запись: staging → проверка → атомарный rename; retry при блокировке
  антивирусом.
- Лимиты архивов.

**Следствия.**

- Нельзя использовать «удобные» абсолютные пути.
- Часть легитимных, но опасных архивов будет отклонена.
- Все файловые операции тестируются отдельно.

**Отклонено.** Доверие путям из архива; запись «как есть»; отключение
антивируса.

## ADR-030. Deferred scope

**Контекст.** Список функций ТЗ шире того, что можно сделать качественно и
проверить.

**Решение.** Вне v1:

- Tauri updater и автоматические обновления;
- OptiFine и LiteLoader;
- ARM64 и Linux/macOS;
- CurseForge;
- приватные и серверные сборки NEXUS через публичный API;
- sidecar-supervisor с восстановлением stdin;
- телеметрия и аналитика;
- синхронизация инстансов между устройствами;
- delta-обновления;
- i18n (только русский, строки вынесены в ресурсы);
- встроенный браузер модов/серверов.

**Следствия.**

- Меньше поверхности для security-ошибок.
- Функции не имитируются «заглушками»: их либо нет, либо они работают.
- Каждый пункт при возвращении требует отдельного ADR и тестов.

**Отклонено.** «Сделать всё сразу»; декоративные кнопки; скрытые заглушки.
